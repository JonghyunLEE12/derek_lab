AgentOS 채널에 올라온 영상을 정리한다. 원본은 AI Engineer 코드 서밋에서 Lauren Tan이 한 발표 <a href="https://youtu.be/O_zcc6Xl12g" target="_blank" rel="noopener noreferrer">All Code Is Slop (Except Mine)</a>이고, 이 영상은 그 발표 클립을 중간중간 틀면서 한국어로 맥락을 풀어 주는 해설 영상이다. 길이는 22분 52초다. 발표자는 Grok Bot이라는 제품을 만드는 팀의 엔지니어이고 스스로를 포테이토라는 닉네임으로 소개한다. 슬롭은 AI가 대충 찍어낸 질 낮은 결과물을 가리키는 말이다.

참고로 이 글은 영상의 한국어 자막을 바탕으로 썼다. 발표 클립 구간은 자막에 거의 잡히지 않아서 해설자가 설명한 내용과 일부 영어 발언만 옮겼다. 숫자는 영상에서 말한 것만 적었고, 해설자 말대로 발표 팀이 직접 제시한 값이라 따로 확인한 숫자는 아니다.

## 한 달 PR 1만 개와 되돌림 0.5%

영상은 숫자로 시작한다. 10월 한 달 동안 한 팀이 병합한 PR이 1만 개가 넘고(영상 설명란 기준 11,000개), 같은 달 되돌린 커밋은 0.5% 안팎이었다. 발표 초반에 나오는 막대 그래프는 팀이 아니라 발표자 한 사람이 달마다 올린 PR 수인데 3월에는 68개였다. 여기까지 오는 데 여섯 달이 걸렸다고 한다.

해설자가 짚는 포인트는 이 영상에서 다루는 장치가 프롬프트나 규칙 파일이 아니라 코드베이스 쪽에 넣는 것들이라는 점이다. 그래서 내 저장소에도 오늘 하나쯤 넣어 볼 수 있다고 한다. 발표 뒤쪽에는 발표자가 직접 만든 플러그인과 자기 팀 제품 이야기도 섞여 있다.

## 포테이토 피라미드

발표 마지막 화면에는 고리가 두 개 있다. 왼쪽 저신뢰 고리에서는 에이전트가 슬롭을 쓰고 사람이 검증하다가 문제를 찾는다. 오른쪽 고신뢰 고리에서는 에이전트가 좋은 코드를 쓰고 검증도 에이전트가 한다. 왼쪽에서 오른쪽으로 가려면 에이전트의 환경 어디에 시간을 써야 하느냐가 발표의 질문이다.

답은 거꾸로 선 삼각형 하나다. 화면에 적힌 이름은 포테이토 피라미드이고 위에서부터 다섯 칸이다.

1. 코드베이스
2. 정적 분석
3. 검증
4. 산문
5. 사람 리뷰

위가 넓고 아래가 좁다. 규칙 파일, 스킬, AGENTS.md 같은 글은 아래쪽 좁은 칸인 산문에 들어간다. 판단이 필요한 것만 조금 적는 자리라는 뜻이다. 해설자는 전에 다룬 Anthropic 발표에서 CLAUDE.md의 감정 문구를 걷어 내라고 한 이야기와 방향이 같다고 덧붙인다. 발표는 가장 넓은 맨 윗칸부터 내려간다.

## 코드베이스: 땜질이 복사되면 패턴이 된다

맨 윗칸에서는 나무로 뒤덮인 건물 그림이 나오고 발표자는 그걸 코드베이스에 빗댄다. 땜질 하나가 복사되고 또 복사돼서 패턴이 된다는 그림이다. 에이전트는 코드베이스에 있는 것을 따라 쓰니까 나쁜 패턴이 한 번 들어오면 계속 번진다는 얘기다.

그러면 실제로는 어떻게 막았나. 팀은 Grok Bot을 만들면서 Dune이라는 자체 프레임워크를 쓰고, 예시는 둘 다 프론트엔드 이야기다.

- **useEffect**: 쓸 수는 있지만 제대로 쓰기 까다로운 기능이다. 제품 코드에서 아예 못 쓰게 했다.
- **화면 코드와 뒤에서 일하는 코드의 혼합**: 섞이면 앱이 버벅인다. 폴더와 린트로 둘을 갈라놨다. 해설자는 백엔드로 치면 서로 다른 프로세스에서 도는 모듈끼리 가져다 쓰지 못하게 경계를 막아 두는 것과 비슷하다고 설명한다.

겉보기엔 다른 두 예시가 한 지점에서 만난다. 두 경우 모두 리뷰에서 다시 볼 일이 없어졌다.

## 정적 분석: 주석 99% 금지

다음 대목은 Cursor에서 있었던 일이다. 화면에 날짜 세 개가 차례로 나온다. 9월 9일에는 화면 깜빡임을 고치려고 setTimeout 한 줄을 넣었다. 그 한 줄 위에는 왜 이 땜질이 괜찮은지 설명하는 주석이 붙어 있었다. 10월 17일쯤에는 타이머가 코드 곳곳으로 퍼져 있었고 클라이언트와 에이전트 성능이 크게 나빠졌다. 타이머가 빠르게 만들어지고 사라지면 가비지 컬렉션이 많이 돌면서 버벅임이 생긴다는 설명이다.

발표자가 꼽은 최악의 부분은 에이전트가 쓴 주석이었다. 주석이 이 임시 처리를 정당화하는 바람에 에이전트에게 제대로 고치지 않아도 되는 빠져나갈 구멍이 됐다. 그래서 Grok Bot에서는 주석의 99%를 금지했다. 이유는 셋이다.

- 주석은 금방 낡는다.
- 사람은 어차피 주석을 잘 안 읽는다.
- 주석은 강제할 수 없다. 다음 에이전트에게 하지 말라고 적어 두는 건 좋은 의도 같지만 믿을 수 있는 장치가 되지 못한다.

대신 린트 규칙을 둔다. 에러 메시지가 에이전트에게 땜질하지 말고 근본 원인을 고치라고 알려 주도록 만든다. 일반 원칙은 이렇다. 에이전트를 교정할 때마다 그 교정을 결정적인 검사로 바꾸거나, 더 나은 API 설계와 아키텍처로 그 문제가 아예 생길 수 없게 만든다. 이걸 충분히 반복하면 코드 리뷰에서 볼 게 줄어들고, 어느 순간 리뷰할 게 남지 않아서 에이전트가 PR 대부분을 스스로 병합하게 둘 수 있다고 한다.

숫자도 나온다. 주석은 7월 말 65,824개에서 지금 1,227개가 됐다. 계단 모양 그래프 하나는 7월에 7에서 시작해 167까지 올라간다. 축 이름은 따로 없지만 교정을 린트나 설계로 옮긴다는 원칙을 말하는 대목에 나온 그래프다. 화면 아래에 지나간 no comments는 발표자가 만든 pstack 플러그인에 들어 있는 스킬 이름이다.

## 검증: 사람은 코드 대신 증거를 본다

발표자가 가장 중요한 단계라고 부르는 건 세 번째 칸 검증이다. 데모 끝에 터미널 명령어 세 줄이 나온다. 앱에서 설정 버튼을 누르고, 화면 상태를 찍고, 스크린샷을 증거 파일로 남기는 명령어다.

에이전트가 PR 대부분을 스스로 병합한다면 사람은 무엇을 보나. 답은 코드가 아니라 검증의 증거다. 영상, 스크린샷, 다이어그램 같은 것들이다. 에이전트가 실제 앱을 직접 돌려 보고 그 증거를 남기는 것이 런타임 검증이다.

그 위에 형식 검증 도구도 쌓았다.

- **TLA+**: 시스템이 가질 수 있는 상태를 전부 펼쳐 놓고 빠뜨린 경우가 없는지 기계가 따져 보게 하는 도구
- **Lean**: 알고리즘이 맞다는 걸 수학 증명처럼 한 단계씩 확인하는 도구
- **속성 기반 테스트**: 예시 몇 개를 손으로 적는 대신 어떤 입력이 와도 지켜져야 하는 조건을 적어 두고 입력을 무작위로 쏟아붓는 방식

발표자는 이것들이 원래 있던 좋은 소프트웨어 엔지니어링 도구라고 말한다. 다만 이해하고 작성하고 유지하기 어려워서 예전에는 쓰기에 너무 비쌌다. 에이전트가 그 비용을 크게 줄였기 때문에 예전보다 훨씬 많은 것을 테스트할 수 있게 됐고, 발표자는 이걸 소프트웨어 테스트와 검증의 황금기라고 부른다. 형식 검증은 제품이 어떻게 동작해야 하는지, 에이전트가 내 의도를 정말 이해했는지 따져 보는 데도 도움이 된다고 한다. 발표자는 사용자 관점에서 상태 기계를 시각화하는 statechart라는 스킬도 pstack에 만들었고, 영상과 스크린샷과 함께 보면 리뷰가 훨씬 쉽다고 했다.

이어서 트윗 두 장이 나온다. 여섯 달쯤 간격을 두고 쓴 글이다. 5월 트윗은 미묘한 버그가 있는 AI 생성 PR 여러 개가 병합돼서 고치느라 며칠이 더 들고 수작업 검증도 많이 필요했다는 내용이다. 11월 트윗은 하루에 쓰는 토큰의 70%가 검증으로 간다는 내용이다.

## 그래서 무엇을 얻었나

여기까지가 투자다. 코드베이스를 정리하고, 교정을 린트로 옮기고, 검증을 여러 겹으로 쌓는 일이다. 돌아온 것은 차트 다섯 장으로 나온다.

1. 팀이 병합한 PR 수
2. 데스크톱 앱 릴리스 횟수
3. 기여한 사람 수 (막대 색은 한 사람이 올린 PR 수 구간)
4. 이 속도에서 되돌림 비율의 변화
5. 앱 성능 표

릴리스는 말로는 하루에 한 번쯤이라고 했는데 슬라이드에 적힌 릴리스 간격 중앙값은 9월 25시간, 10월 28시간이다. 성능 표 아래에는 Electron 앱에는 천장이 있어서 Rust로 다시 쓰는 것도 생각하는 중이라는 작은 글씨가 한 줄 있었다.

## 소프트웨어 공장보다 먼저

이 결과를 보고 자동화부터 시작하면 되느냐는 질문에 대한 발표자의 답은 순서다. 코드를 쓰는 안쪽 루프가 슬롭을 내고 있으면 그 루프를 자동화해도 슬롭만 더 많이 나온다. 그래서 새로 생기는 안티 패턴을 린트로 먼저 막고 이미 있는 건 그다음에 치운다.

이 기초 위에 팀이 올린 것이 마지막 예시다. 발표자는 자기 팀 제품인 Grok Bot을 이 바깥 루프로 쓰라고 권한다. X에 올라온 피드백, 이슈 티켓, 슬랙 메시지, 모니터링 알림 같은 신호가 들어오면 Grok Bot이 에이전트를 띄워 일을 시작하는 그림이다. 새 릴리스를 낼 때마다 앱에 온갖 입력과 조작을 마구 던져 깨지는 곳을 찾는 퍼징이 돌고 그 결과가 슬랙 스레드로 보고된다고 한다.

발표는 처음 제목으로 돌아가 끝난다. 마지막 슬라이드에서는 괄호 안의 "내 것만 빼고"가 "여러분 것만 빼고"로 바뀌어 있다.

## 정리

- 에이전트 코드를 믿을 수 있게 만드는 장치는 피라미드 위쪽일수록 효과가 크다. 코드베이스와 정적 분석이 가장 넓은 칸이고 규칙 파일 같은 산문은 좁은 칸이다.
- 에이전트를 교정할 때마다 그 교정을 린트 같은 결정적 검사나 API·아키텍처 설계로 옮긴다. 주석은 강제할 수 없고 땜질의 핑계가 되기 쉬워서 거의 다 금지했다.
- 가장 중요한 칸은 검증이다. 사람은 코드 대신 에이전트가 남긴 영상, 스크린샷, 다이어그램 같은 증거를 본다. 에이전트 덕에 형식 검증과 속성 기반 테스트의 비용이 내려갔다.
- 자동화는 순서가 먼저다. 안쪽 루프가 슬롭을 내면 바깥 루프를 자동화해도 슬롭만 늘어난다.

해설자의 마무리 제안도 크지 않다. 에이전트가 같은 실수를 해서 또 고쳐 줬다면 규칙 파일에 한 줄 보태기 전에 린트 규칙이나 테스트로 만들 수 있는지 먼저 본다. 새로 생기는 것부터 막고 이미 있는 건 그다음에 지운다. 그리고 에이전트가 자기 결과를 직접 실행해서 확인할 방법을 하나 열어 준다. 주석을 거의 다 없애는 일이나 PR 자동 병합은 별개 이야기다. 발표자도 여기까지 여섯 달이 걸렸고 팀의 숫자는 그 팀의 코드베이스에서 나온 것이다.

## 내 생각

에이전트가 틀린 걸 고치고 나면 CLAUDE.md에 한 줄 적는 게 가장 손쉬운 대응인데, 피라미드로 보면 그건 아래쪽 좁은 칸에만 쌓는 일이다. 같은 실수가 두 번 나오면 그걸 린트나 테스트로 바꿀 수 있는지 먼저 보는 습관은 바로 들여 볼 만하다.

검증 칸도 와닿았다. 사람이 코드를 읽는 대신 증거를 본다는 방향은 리뷰를 줄이는 게 아니라 리뷰 대상을 바꾸는 이야기라서, 에이전트가 스크린샷이나 테스트 출력을 남기게 하는 것부터 시작하면 될 것 같다.
