AgentOS 채널에 올라온 영상을 정리한다. 원본은 AI Engineer 코드 서밋에서 Lauren Tan이 한 발표 <a href="https://youtu.be/O_zcc6Xl12g" target="_blank" rel="noopener noreferrer">All Code Is Slop (Except Mine)</a>이고, 이 영상은 그 발표 클립을 중간중간 틀면서 한국어로 맥락을 풀어 주는 해설 영상이다. 길이는 22분 52초다. 발표자는 Grok Bot이라는 제품을 만드는 팀의 엔지니어이고 스스로를 포테이토라는 닉네임으로 소개한다. 슬롭은 AI가 대충 찍어낸 질 낮은 결과물을 가리키는 말이다.

참고로 이 글은 영상의 한국어 자막을 바탕으로 썼다. 발표 클립 구간은 자막에 거의 잡히지 않아서 해설자가 설명한 내용과 일부 영어 발언만 옮겼다. 캡처를 넣으면서 슬라이드에 적힌 글자와 화면에 박힌 자막에서 읽은 내용을 조금 보탰다. 숫자는 영상에 나온 것만 적었고, 해설자 말대로 발표 팀이 직접 제시한 값이라 따로 확인한 숫자는 아니다.

흐름이 있는 부분은 움직이는 다이어그램 다섯 개로 옮겼고 슬라이드는 캡처로 넣었다. 해설 영상은 발표 화면을 그대로 보여 주는 구간과 해설자가 슬라이드를 다시 그려 설명하는 구간이 섞여 있어서 캡처도 두 종류다. 캡션 끝의 시각은 유튜브의 그 지점으로 가는 링크다.

## 한 달 PR 1만 개와 되돌림 0.5%

영상은 숫자로 시작한다. 10월 한 달 동안 한 팀이 병합한 PR이 1만 개가 넘고(영상 설명란 기준 11,000개), 같은 달 되돌린 커밋은 0.5% 안팎이었다. 발표 초반에 나오는 막대 그래프는 팀이 아니라 발표자 한 사람이 달마다 올린 PR 수인데 3월에는 68개였다. 슬라이드 제목은 "지난달 PR 3,000개를 프로덕션에 냈다"이고 마지막 막대는 3,129다. 여기까지 오는 데 여섯 달이 걸렸다고 한다.

해설자가 짚는 포인트는 이 영상에서 다루는 장치가 프롬프트나 규칙 파일이 아니라 코드베이스 쪽에 넣는 것들이라는 점이다. 그래서 내 저장소에도 오늘 하나쯤 넣어 볼 수 있다고 한다. 발표 뒤쪽에는 발표자가 직접 만든 플러그인과 자기 팀 제품 이야기도 섞여 있다.

## 포테이토 피라미드

슬라이드 'help agents write good code'에는 고리가 두 개 있다. 왼쪽 저신뢰 고리에서는 에이전트가 슬롭을 쓰고 사람이 검증하다가 문제를 찾는다. 슬라이드 작은 글씨로는 대부분의 사람이 여기 머물러 있다. 오른쪽 고신뢰 고리에서는 에이전트가 좋은 코드를 쓰고 검증도 에이전트가 한다. 왼쪽에서 오른쪽으로 가려면 에이전트의 환경 어디에 시간을 써야 하느냐가 발표의 질문이다. 발표가 끝날 무렵 같은 고리 그림이 한 번 더 나온다.

<VideoFrame src={trustLoops} alt="해설자가 다시 그린 발표 슬라이드 'help agents write good code'. 왼쪽 low trust 고리는 agent writes slop code, human verifies it, issues found 세 단계로 돌고 오른쪽 high trust 고리는 agent writes good code, agent verifies it, issues found로 돈다. 두 고리 사이 화살표에 주황 테두리가 쳐져 있다. 아래 칩은 여섯 달, 저신뢰 · 사람이 검증, 고신뢰 · 에이전트가 검증이고 마지막 칩이 강조돼 있다." caption="저신뢰 고리에서 고신뢰 고리로. 바뀌는 자리는 검증하는 쪽이 사람에서 에이전트로 넘어가는 곳이다." time="02:56" videoUrl={videoUrl} />

답은 거꾸로 선 삼각형 하나다. 화면에 적힌 이름은 포테이토 피라미드이고 위에서부터 다섯 칸이다.

1. 코드베이스
2. 정적 분석
3. 검증
4. 산문
5. 사람 리뷰

위가 넓고 아래가 좁다. 규칙 파일, 스킬, AGENTS.md 같은 글은 아래쪽 좁은 칸인 산문에 들어간다. 판단이 필요한 것만 조금 적는 자리라는 뜻이다. 해설자는 전에 다룬 Anthropic 발표에서 CLAUDE.md의 감정 문구를 걷어 내라고 한 이야기와 방향이 같다고 덧붙인다. 발표는 가장 넓은 맨 윗칸부터 내려간다.

## 코드베이스: 땜질이 복사되면 패턴이 된다

맨 윗칸에서는 나무로 뒤덮인 건물 그림이 나오고 발표자는 코드베이스를 정원에 빗댄다. 코드가 끊임없이 들어와서 살아 있는 것처럼 느껴지고, 에이전트가 쓰는 새 코드는 이미 있는 코드를 기초 삼아 자란다는 얘기다. 이어지는 그림에서는 잡초 하나가 땅속 뿌리로 옆 잡초에 이어지면서 줄줄이 번진다. 슬라이드 제목은 "복사본 하나가 다음 복사본을 더 그럴듯하게 만든다"이고 왼쪽 끝은 땜질 하나, 오른쪽은 패턴이라고 적혀 있다. 에이전트는 코드베이스에 있는 것을 따라 쓰니까 나쁜 패턴이 한 번 들어오면 계속 번진다.

<VideoFrame src={eachCopy} alt="발표 화면. 슬라이드 제목은 each copy makes the next copy more likely. 땅 위에 잡초 여섯 포기가 나란히 있고 땅속 뿌리가 서로 이어져 있다. 위쪽에 copy라고 적힌 화살표 세 개가 오른쪽을 가리킨다. 왼쪽 아래에 one workaround, 오른쪽 아래에 the pattern이라고 적혀 있다. 하단 자막은 다음 에이전트가 그냥 베낄 가능성이 커요. 코드베이스의 확립된 패턴처럼 보이니까요." caption="땜질 하나(one workaround)가 복사를 거쳐 패턴(the pattern)이 된다." time="06:04" videoUrl={videoUrl} />

그러면 실제로는 어떻게 막았나. 팀은 Grok Bot을 만들면서 Dune이라는 자체 프레임워크를 쓴다. 슬라이드에서 Dune은 앱 프레임워크에 세 가지를 더한 것으로 나온다. 기능마다 폴더 하나, 엄격한 import 금지, 코드 안 주석 금지다. 발표자는 기술적으로 흥미로운 프레임워크는 아니고 제약과 린트 규칙이 많은 게 흥미로운 점이라고 했다.

<VideoFrame src={duneFramework} alt="발표 화면. 슬라이드 제목은 dune: a framework for agents. 왼쪽 상자에 app framework, 그 아래 작은 글씨로 navigation, rendering, IPC. 더하기 기호 오른쪽에 세 상자가 세로로 있다. one folder per feature는 파란 테두리, strict import bans는 초록 테두리, no comments in code는 주황 테두리다." caption="Dune은 앱 프레임워크에 폴더 규칙, import 금지, 주석 금지를 더한 것이다." time="06:56" videoUrl={videoUrl} />

해설에서 다룬 예시는 둘 다 프론트엔드 이야기다.

- **useEffect**: 쓸 수는 있지만 제대로 쓰기 까다로운 기능이다. 제품 코드에서 아예 못 쓰게 했다.
- **화면 코드와 뒤에서 일하는 코드의 혼합**: 섞이면 앱이 버벅인다. 폴더와 린트로 둘을 갈라놨다. 해설자는 백엔드로 치면 서로 다른 프로세스에서 도는 모듈끼리 가져다 쓰지 못하게 경계를 막아 두는 것과 비슷하다고 설명한다.

두 번째 예시는 슬라이드 'directory structure is a form of context'에 그림으로 나온다. 화면 쪽 electron-renderer 폴더와 뒤에서 일하는 electron-main 폴더 사이에 X 표시가 있고 그 아래에 "not even types"라고 적혀 있다. 같이 쓰는 타입은 shared 폴더에만 둔다. 화면에 박힌 자막에 따르면 에이전트가 메인 스레드 코드를 렌더 스레드로 자주 import했고, 그래서 둘 사이 import를 의존성 그래프 분석기와 린트 규칙 몇 개로 막았다.

<VideoFrame src={directoryStructure} alt="발표 화면. 슬라이드 제목은 directory structure is a form of context. 위쪽 Dune 영역 왼쪽에 electron-renderer 폴더(features, client, primitives), 오른쪽에 electron-main 폴더(startup, notifications, update)가 있고 둘 사이 화살표에 X와 not even types가 적혀 있다. 가운데 아래 shared 상자에 shared types. 아래쪽에는 tibo.dog (side project) 예시가 있다. 하단 자막은 그 둘 사이의 import는 의존성 그래프 분석기와 린트 규칙 몇 개로 막아 뒀어요." caption="렌더러와 메인 사이에는 타입조차 오가지 못한다. 공유 타입은 shared에만 둔다." time="08:40" videoUrl={videoUrl} />

겉보기엔 다른 두 예시가 한 지점에서 만난다. 두 경우 모두 리뷰에서 다시 볼 일이 없어졌다.

## 정적 분석: 주석 99% 금지

## 검증: 사람은 코드 대신 증거를 본다

발표자가 가장 중요한 단계라고 부르는 건 세 번째 칸 검증이다. 에이전트가 PR 대부분을 스스로 병합한다면 사람은 무엇을 보나. 답은 코드가 아니라 검증의 증거다. 영상, 스크린샷, 다이어그램 같은 것들이다. 에이전트가 실제 앱을 직접 돌려 보고 그 증거를 남기는 것이 런타임 검증이다.

슬라이드 'runtime verification'은 두 부분이다. 왼쪽 피처 맵은 어떤 기능이 있고, 사용자가 어떻게 닿고, 무엇이 동작을 증명하는지 잇는 그림이다. 화면에 박힌 자막으로는 사용자 관점에서 앱의 모든 기능을 담은 사이트맵 같은 것이고 이걸로 공통 어휘가 생긴다. 오른쪽은 터미널 명령어 세 줄이다. 앱에서 설정 버튼을 누르고, 화면 상태를 찍고, 스크린샷을 증거 파일로 남긴다. 스킬 안에 전용 CLI를 둬서 에이전트가 매번 같은 CLI와 드라이버를 다시 쓴다.

## 소프트웨어 공장보다 먼저

이 결과를 보고 자동화부터 시작하면 되느냐는 질문에 대한 발표자의 답은 순서다. 코드를 쓰는 안쪽 루프가 슬롭을 내고 있으면 그 루프를 자동화해도 슬롭만 더 많이 나온다. 그래서 새로 생기는 안티 패턴을 린트로 먼저 막고 이미 있는 건 그다음에 치운다.

이 기초 위에 팀이 올린 것이 마지막 예시다. 발표자는 자기 팀 제품인 Grok Bot을 이 바깥 루프로 쓰라고 권한다. X에 올라온 피드백, 이슈 티켓, 슬랙 메시지, 모니터링 알림 같은 신호가 들어오면 Grok Bot이 에이전트를 띄워 일을 시작하는 그림이다. 새 릴리스를 낼 때마다 앱에 온갖 입력과 조작을 마구 던져 깨지는 곳을 찾는 퍼징이 돌고 그 결과가 슬랙 스레드로 보고된다고 한다.

## 정리

- 에이전트 코드를 믿을 수 있게 만드는 장치는 피라미드 위쪽일수록 효과가 크다. 코드베이스와 정적 분석이 가장 넓은 칸이고 규칙 파일 같은 산문은 좁은 칸이다.
- 에이전트를 교정할 때마다 그 교정을 린트 같은 결정적 검사나 API·아키텍처 설계로 옮긴다. 주석은 강제할 수 없고 땜질의 핑계가 되기 쉬워서 거의 다 금지했다.
- 가장 중요한 칸은 검증이다. 사람은 코드 대신 에이전트가 남긴 영상, 스크린샷, 다이어그램 같은 증거를 본다. 에이전트 덕에 형식 검증과 속성 기반 테스트의 비용이 내려갔다.
- 자동화는 순서가 먼저다. 안쪽 루프가 슬롭을 내면 바깥 루프를 자동화해도 슬롭만 늘어난다.

해설자의 마무리 제안도 크지 않다. 에이전트가 같은 실수를 해서 또 고쳐 줬다면 규칙 파일에 한 줄 보태기 전에 린트 규칙이나 테스트로 만들 수 있는지 먼저 본다. 새로 생기는 것부터 막고 이미 있는 건 그다음에 지운다. 그리고 에이전트가 자기 결과를 직접 실행해서 확인할 방법을 하나 열어 준다. 주석을 거의 다 없애는 일이나 PR 자동 병합은 별개 이야기다. 발표자도 여기까지 여섯 달이 걸렸고 팀의 숫자는 그 팀의 코드베이스에서 나온 것이다.

## 내 생각

에이전트가 틀린 걸 고치고 나면 CLAUDE.md에 한 줄 적는 게 가장 손쉬운 대응인데, 피라미드로 보면 그건 아래쪽 좁은 칸에만 쌓는 일이다. 같은 실수가 두 번 나오면 그걸 린트나 테스트로 바꿀 수 있는지 먼저 보는 습관은 바로 들여 볼 만하다.

검증 칸도 와닿았다. 사람이 코드를 읽는 대신 증거를 본다는 방향은 리뷰를 줄이는 게 아니라 리뷰 대상을 바꾸는 이야기라서, 에이전트가 스크린샷이나 테스트 출력을 남기게 하는 것부터 시작하면 될 것 같다.
