## 어드민 하나를 만드는 과정

발표는 어드민 서비스 하나를 만들 때 프론트엔드에서 거치는 과정을 세면서 시작한다. 슬라이드에는 여섯 단계가 있다.

1. 프로젝트를 스캐폴딩한다.
2. 의존성을 추가한다.
3. 빌드 도구를 선택한다.
4. 인증을 연동한다.
5. 배포를 설정한다.
6. 코드를 작성해서 빌드하고 배포한다.

서버에서 API를 준비하는 과정도 따로 있다. 어드민은 여기서 끝나지 않고 일반적인 웹 서비스 개발 과정에 네 가지가 더 붙는다. 개인정보 마스킹, 정보 조회 사유 수취, 다운로드 사유 수취, 다운로드 파일 암호화다.

## AI로 만드는 어드민

### 데모

"토스에서는 어드민을 AI로 만듭니다"라는 슬라이드 다음에 발표자가 시연 영상을 틀었다. 화면 왼쪽 위에 TOI studio라는 이름이 보인다. 프롬프트를 보내면 화면이 둘로 나뉜다. 왼쪽이 프리뷰(Preview)이고 오른쪽이 채팅이다. 순서는 이렇다.

1. 사용자가 "데이터 조회 어드민을 만들어주세요."라고 입력한다.
2. AI가 되묻는다. 어떤 데이터를 조회할지, 상세 패널과 검색 필터와 다운로드 버튼이 필요한지 묻는다. 발표자는 Ask User Question 같은 기능이라고 설명했다.
3. 사용자가 답한다.
4. 에이전트가 계획을 세우고 코드를 쓴다. 그동안 프리뷰에는 "화면을 만들고 있어요"가 떠 있다.
5. 몇 분 뒤 프리뷰에 사용자 관리 화면이 나타난다. 표의 이메일과 전화번호는 일부가 별표로 가려져 있다.

### 만든 이유

토스는 비즈니스를 빠르게, 많이 진행하고 그만큼 그 비즈니스를 관리할 어드민 수요가 꾸준히 생긴다. 그런데 FE 리소스가 없는 팀은 어드민을 만들지 못했다. 서버 개발자가 직접 만들어서 따로 쓰는 경우도 있었다. 만들 때마다 앞의 과정을 반복했고 슬라이드 표현으로는 개발, 보안, 배포 비용이 수요만큼 같이 커졌다.

## 정책과 화면 분리

발표자는 어드민에 필요한 일을 둘로 나눴다. 데이터를 다루는 정책은 플랫폼이 맡고 데이터를 보여주는 화면은 AI가 만든다.

플랫폼 쪽은 이렇게 동작한다. API를 등록해 두면 플랫폼 서버가 그 API를 프록시한다. 호출이 프록시를 지나가므로 정책이 자동으로 적용되는데 마스킹, 조회 사유, 암호화가 이 정책이다. 호출 기록도 프록시에서 자동으로 남는다.

화면 쪽은 AI가 API 스키마를 참고해서 React 코드를 생성한다. 테이블, 필터, 상세 페이지처럼 자주 쓰는 패턴은 구성 방법을 AI에게 미리 알려 뒀다. 사용자는 자연어로 요청하면 된다.

## 브라우저 실행 환경

### AI가 만든 코드를 실행할 곳

프론트엔드 개발자는 로컬 개발 환경에서 코드를 실행하고 프리뷰를 확인하면서 개발한다. AI가 만든 코드는 사용자의 브라우저에서 프리뷰로 보여 줘야 한다. 그래서 개발 환경을 브라우저 안으로 가져와야 했다. 슬라이드에는 "코드를 만드는 일과 그 코드가 화면이 되는 일은 서로 달라요"라고 적혀 있다.

### 시도 1, 개발 서버 공유

첫 시도는 Next.js 개발 서버(Dev Server) 하나를 서버에 띄우는 방식이었다. 프로세스 하나가 모든 프로젝트 파일을 함께 감시하고 사용자마다 iframe으로 그 프로세스에 연결한다. 로컬에서 개발하던 방식을 그대로 서버로 옮긴 것이고 PoC로는 충분했다.

문제는 격리였다. 사용자 A가 A 페이지를 편집하다가 컴파일 에러를 내면 에러 오버레이가 개발 서버 전체로 퍼진다. B 페이지를 보던 사용자 B에게도, C 페이지를 보던 사용자 C에게도 같은 "Failed to compile"이 보인다. 실행 환경을 사용자별로 나누지 않아서 생긴 문제였다.

### 시도 2, Sandpack

다음에는 실행 위치를 브라우저로 옮겼다. 사용자 수만큼 서버를 띄우는 대신 모든 사용자가 가진 실행 환경인 브라우저를 쓰기로 했다. 이때 쓴 도구가 Sandpack이다. Sandpack은 코드 샌드박스를 만들어 프리뷰를 제공하는 라이브러리다. 진행자는 공식 문서에서 코드를 고치면 UI가 바로 바뀌는 예제를 떠올리면 된다고 덧붙였다. iframe 위에 가상 환경을 만들어 띄우는 방식이다.

격리는 성공했다. A의 코드는 A의 브라우저에서만 실행되고 에러도 A에게만 보인다.

<AiAdminErrorIsolation />

하지만 느렸다. 프리뷰 첫 화면이 보이기까지 47초가 걸렸다. Sandpack은 브라우저 런타임에 진입한 시점부터 패키지를 내려받기 때문이다. 슬라이드에는 "매번, 모든 사용자가, 처음부터"라고 적혀 있다. 패키지를 퍼블릭 레지스트리에서 받아 오는 형태라 사내 패키지를 넣기도 어려웠다.

## Preview Runtime 직접 구현

시도 두 번이 다 막힌 뒤 직접 만들기로 했다. 47초 슬라이드 맨 아래에는 "필요한 시점에 미리 준비해 두는 구조를 직접 만들기로 했어요"라고 적혀 있다. 이렇게 만든 것이 Preview Runtime이고 포인트는 세 가지다.

1. 실시간으로 바뀌는 코드는 사용자 브라우저에서 빌드한다. 가상 파일 시스템 위에서 esbuild-wasm으로 빌드한다.
2. 사용할 패키지는 미리 준비한다. 조합이 바뀔 때 한 번만 빌드해서 바로 가져다 쓴다.
3. 실행한 결과물은 화면에 보여준다. 빌드가 끝나면 문서를 통째로 교체한다.

### 가상 파일 시스템

브라우저에는 파일 시스템이 없다. 그래서 경로를 키로 해서 파일 내용을 연결하는 가상 파일 시스템을 만들었다. 레이어는 네 개다. 빌드 도구가 `./components/Table` 같은 경로를 찾으면 위 레이어부터 순서대로 본다. 맨 위는 userLayer이고 AI가 만들고 사용자가 편집하는 페이지 코드가 들어 있다. 그 아래 projectLayer에는 여러 페이지가 공유하는 프로젝트 코드가 있다. templateLayer에는 Preview Shell 템플릿이, runtimeLayer에는 Preview Runtime 코드가 있다.

### esbuild-wasm 번들

esbuild-wasm은 esbuild를 웹어셈블리(WebAssembly) 버전으로 만들어 브라우저에서 실행할 수 있게 한 라이브러리다. 발표자는 가상 파일 시스템을 esbuild-wasm에 플러그인으로 연결했다. esbuild-wasm이 import 구문을 해석하다가 파일을 요청하면 플러그인이 가상 파일 시스템에서 내용을 돌려준다. esbuild-wasm은 TypeScript와 JSX를 변환하고 import 그래프를 따라가서 파일을 하나로 묶는다. 슬라이드에서 esbuild-wasm 아래에는 Web Worker라는 라벨이 붙어 있다. 결과물은 브라우저가 바로 실행할 수 있는 ESM 번들이다.

react나 @tds/desktop 같은 패키지는 이 번들에 넣지 않는다. external로 남겨 두고 실행할 때 import map이 연결한다. 진행자는 브라우저에서도 Node.js 같은 런타임처럼 돌아가게 한 것이라고 정리했다.

### 패키지 조합

앱 코드를 빌드하는 과정은 여기까지이고 발표자가 고민을 더 많이 한 쪽은 패키지다. 처음에는 모든 프로젝트가 같은 패키지 조합을 썼다. react, @tds/desktop, 유틸리티 몇 개였다. 그런데 프로젝트마다 다른 패키지를 쓰고 싶다는 요청이 계속 들어왔다. 고정된 조합을 중앙에서 하나로 관리하면 패키지를 하나 넣을 때마다 충돌을 확인해야 한다. 버전을 올리면 모든 프로젝트가 영향을 받는다.

그래서 패키지를 하나씩 따로 번들링해 봤다. 이번에는 싱글톤이 깨졌다. 슬라이드의 예는 @tanstack/react-query와 @suspensive/react-query다. @tanstack/react-query를 따로 번들링했는데 @suspensive/react-query 번들에도 의존성인 react-query 모듈이 함께 들어갔다. react-query 모듈 복사본이 두 개가 된 것이다. 같은 모듈인데 서로 다른 인스턴스를 참조해서 런타임 오류가 났다. 어떤 패키지가 하나만 존재해야 하는지는 그 패키지만 봐서는 알 수 없다. 그래서 단위를 개별 패키지에서 조합으로 바꿨다.

<VideoFrame src={singletonBrokenBundles} alt="발표 슬라이드 '② 패키지를 하나씩 나눌 수 없었던 이유'. 왼쪽 위에 @tanstack/react-query, 따로 번들링했어요, react-query 모듈 1번째 복사본. 왼쪽 아래에 @suspensive/react-query, 이 번들에도 의존성이 함께 들어갔어요, react-query 모듈 2번째 복사본. 오른쪽으로 가는 화살표 끝에 경고 표시와 런타임 오류, 같은 모듈인데 서로 다른 인스턴스를 참조했어요, 하나만 존재해야 하는 패키지는 패키지만 봐서는 알 수 없어요. 아래에 개별 패키지가 아니라 조합이 단위여야 했어요라고 적혀 있다." caption="패키지를 하나씩 번들링하자 react-query 모듈 복사본이 둘이 됐다." time="09:05" videoUrl={videoUrl} />

### packageSetHash

조합에 붙인 이름이 packageSetHash다. 재료는 두 가지다. 하나는 브라우저에 공개하는 entry 목록이고 순서가 달라도 결과가 같도록 정렬한다. 다른 하나는 Yarn이 확정한 lockfile 해시이고 여기에는 전이 의존성 버전까지 반영돼 있다. 이 둘을 sha256으로 함께 해싱한다. 결과 문자열을 package.json에 기록하고 같은 조합인지는 이 문자열로 판별한다.

조합을 만드는 일은 서버가 미리 한다. 패키지 조합이 바뀔 때 한 번만 한다.

1. 빈 워크스페이스에 package.json을 복사한다.
2. yarn install로 의존성을 확정한다.
3. Vite로 브라우저용 패키지 파일을 빌드한다.
4. 빌드한 파일을 import map과 함께 S3의 해시 경로에 올린다.

브라우저는 프리뷰를 열 때마다 가져다 쓰기만 한다.

1. package.json에서 packageSetHash를 읽는다.
2. 해시 경로에서 importmap.json을 받는다.
3. external로 남긴 패키지를 실제 파일에 연결한다.
4. 같은 조합이면 캐시를 재사용한다.

### 문서 전체 교체

남은 일은 ESM 번들과 패키지를 합쳐서 화면에 보여주는 것이다. 빌드가 끝날 때마다 새 HTML 문서를 만들어서 번들을 실행한다. 실행에 성공하면 iframe을 통째로 교체하고 이전 문서의 DOM, 상태, 전역 값은 전혀 남지 않는다. 실행에 실패하면 교체하지 않고 마지막 정상 화면을 유지한 채 에러 오버레이만 띄운다. 슬라이드에서는 성공 쪽이 커밋이고 실패 쪽이 롤백이다. 프리뷰 업데이트가 트랜잭션 커밋처럼 동작해서 사용자는 성공한 최신 화면만 본다.

## 회고

회고 슬라이드의 제목은 "돌아보면, 결국 구조를 잘 설계하는 일"이다. 발표자가 말한 엔지니어의 일은 이렇다. 제품의 요구에 맞게 경계를 정하고 변화해야 하는 부분과 더 느리게 변화할 부분을 가려서 인터페이스를 정한다. 그리고 코드가 안전하고 빠르게 실행되는 구조를 만든다.

발표자는 본인이 직접 구현한 부분은 거의 없다고 봐도 된다고 했다. 이미 잘 쓰이는 라이브러리와 도구를 조합해서 시스템을 만들었기 때문이다. 슬라이드에는 도구 네 개가 맡은 일과 함께 적혀 있다. 앱 코드 빌드는 esbuild-wasm, 의존성 설치와 버전 해석은 Yarn, 패키지 사전 빌드는 Vite, 패키지 연결은 import map이다. 이런 도구를 잘 쓰고 조합하는 일도 엔지니어가 해야 하는 일이라고 덧붙였다.

마지막 슬라이드는 "10x Engineer 에서 10x Organization 으로"다. 조직의 문제를 잘 구조화해서 AI를 활용한 제품으로 만들면 그게 조직 전체의 10x를 만든다는 말이다. 토스에서 이런 시도를 많이 하고 있다고 했다.

## 질문 하나

편집본에는 질문이 하나 나온다. 브라우저에 파일 시스템이 없어서 비슷한 걸 만들었다는데 파일이 실제로 디스크에 써져서 남는지, 런타임이 종료될 때 회수되는지를 물었다. 발표자는 후자라고 답했다. 가상 파일 시스템은 메모리에서만 쓴다. 실제 코드는 S3에 있고 사용자가 편집하는 대로 업데이트된다.

## 내 생각

47초가 1.3초가 된 이유를 슬라이드는 패키지를 받는 시점으로 적었다. 자주 바뀌는 앱 코드는 브라우저에서 그때그때 빌드하고 잘 안 바뀌는 패키지는 조합이 바뀔 때만 서버에서 빌드해 둔다. 회고에서 말한 변화하는 부분과 더 느리게 변화하는 부분의 경계가 여기에 그대로 있다. 패키지를 하나씩 나눴다가 싱글톤이 깨진 뒤 단위를 조합으로 올린 것도 그 경계를 다시 그은 일로 보인다.

정책과 화면을 나눈 구조도 비슷하게 읽었다. 마스킹이랑 호출 기록을 프록시가 맡으니 화면 코드를 AI가 만들어도 정책은 따로 지켜진다. FE 리소스가 없는 팀이 자연어로 어드민을 만들 수 있는 것도 그래서인 것 같다. 발표자는 직접 구현한 부분이 거의 없다고 했는데 esbuild-wasm, Yarn, Vite, import map 중에 새로 만든 건 실제로 없다. 가상 파일 시스템 플러그인이랑 packageSetHash처럼 도구 사이를 잇는 부분이 직접 만든 쪽으로 보인다.
