## RCA 과정 개요

RCA는 Root Cause Analysis의 줄임말이다. 문제의 근본 원인을 찾아가는 과정을 뜻한다. 발표에서는 과정을 다섯 단계로 나눈다.

<RcaCycle caption="문제 인지 뒤에 자료 수집, 특이점 파악, 가설 생성, 가설 검증이 이어진다. 가설 검증에서 자료 수집으로 돌아가는 선이 반복 구간이다." />

자료 수집부터 가설 검증까지는 한 번에 끝나지 않는다. 납득할 만한 결과가 나올 때까지 여러 번 돈다. 발표의 사례도 두 사이클을 돌아서 끝난다.

## 문제 인지

시스템이나 담당자에게 문제 상황을 알리는 단계다. 토스증권은 여기서 두 가지 목표를 잡았다. 첫째는 인지 시간 단축, 둘째는 알람 내용을 풍부하게 하는 것이다.

인지 시간은 전체 처리 시간을 좌우한다. 인지가 늦으면 뒤의 모든 단계가 같이 늦어진다. 정보가 부족한 알람도 문제다. 알람만 오면 담당자가 자료를 전부 손으로 모아야 한다. 그래서 뒤 단계인 특이점 파악과 가설 생성에 쓸 기본 정보를 알람에 같이 넣기로 했다.

### 인지 시간 단축: Flink 기반 스트리밍 집계

인지 시간을 줄이기 위해 스트리밍 데이터 파이프라인인 Apache Flink를 도입했다. 구조는 이렇다.

<FlinkAlertPipeline caption="애플리케이션 로그가 Kafka로 들어가면 Flink job이 바로 집계한다. threshold를 넘은 결과만 다시 Kafka를 거쳐 알람 시스템으로 간다." />

애플리케이션은 원래 로그 적재를 위해 로그를 Kafka로 보내고 있었다. Flink job이 이 Kafka를 직접 consume한다. 서비스명과 path를 기준으로 keyBy 하고 window로 집계한다. 집계 결과가 정해진 threshold를 넘으면 다시 Kafka로 보낸다. 알람 시스템은 그 토픽을 consume해서 알람을 보낸다.

중간 저장소가 없다. Kafka에서 가져온 레코드를 바로 집계한다. 기존 시스템에서는 첫 알람까지 수 분이 걸렸는데, 이 구조로 바꾸고 수 초 수준으로 줄었다고 한다.

<VideoFrame src={flinkPipeline} alt="발표 슬라이드 '1. 문제 인지 - 인지시간 단축'. 왼쪽에 Log Kafka, Flink job, Kafka, alert creator 네 상자가 이어져 있고 오른쪽에 keyBy와 window, aggregate를 호출하는 Flink 코드가 있다." caption="원본 슬라이드. 오른쪽 코드에서 서비스명과 path로 keyBy 하고 window로 집계하는 부분을 볼 수 있다." time="01:31" videoUrl={videoUrl} />

### 알람 내용 보강: 변경 이력

두 번째 목표에서 먼저 주목한 영역은 변경 이력이다. 대부분의 이슈는 변경에서 비롯된다. 그래서 알람에 변경 이력을 같이 보내기로 했다.

<ChangeHistoryAggregator caption="aggregator가 프런트엔드 배포, 백엔드 배포, 인프라 작업 이력을 모아 체인지 스토리 DB에 쌓는다. 알람 시스템은 이 뷰를 읽어 알람의 뒤쪽 두 섹션을 채운다." />

방법은 aggregator 레이어다. 프런트엔드 배포, 백엔드 배포, 인프라 작업 이력 같은 여러 종류의 변경 이력을 가져와서 체인지 스토리라는 이름의 중앙 DB에 저장한다. 결과로 변경 이력에 대한 통일된 뷰가 생겼다. 뷰에서 클라이언트는 프런트엔드 배포 이력, 서비스는 백엔드 배포 이력, 나머지는 각각의 작업 이력이다. 알람 시스템은 이 뷰를 읽어서 변경 이력을 알람에 붙인다.

최종 알람은 네 섹션으로 구성된다. 첫 섹션에 에러 통계가 있다. 두 번째 섹션에서는 알람이 수 초 안에 전송됐다는 걸 확인할 수 있다. 세 번째와 네 번째 섹션에 서비스 배포 이력과 인프라 작업 이력이 들어간다.

<VideoFrame src={alertResult} alt="발표 슬라이드 '1. 문제 인지 - 결과'. 왼쪽에 지연과 컨텐츠 목표가 있고 오른쪽에 실제 알람 메시지가 있다. 알람은 서비스 ERROR 발생 건수, 에러 통계, 발생시간, 최근배포, 최근 DB 작업 순서로 구성된다." caption="실제 알람 예시. 에러 통계, 발생 시각, 최근 배포 이력, 최근 DB 작업 이력 순서로 네 섹션이 있다." time="02:33" videoUrl={videoUrl} />

## 자료 수집

원인을 파악하기 위해 필요한 데이터를 모으는 단계다. 토스증권은 여러 도구를 쓴다. 이 단계의 목표는 두 가지다. 자료 수집이 쉬워야 한다는 편의성과, 모은 자료에 누구나 쉽게 접근할 수 있어야 한다는 접근성이다.

### 편의성: 자동 프로파일링

편의성을 위해 어드민 페이지에서 프로파일링을 할 수 있게 지원하고 있었다. 하지만 이슈가 언제 터질지는 예측할 수 없다. 사람이 매번 어드민에 들어가서 프로파일링을 누르는 방식은 지속 가능하지 않았다. 그래서 자동 수집으로 바꿨다.

자동 수집은 두 가지 조건에서 돈다. 지정한 스케줄에 따라 돌거나, 메트릭이 임계치에 도달했을 때 돈다. 증권업은 피크 트래픽 타이밍이 어느 정도 예측된다. 그래서 스케줄 기반 전략을 쓸 수 있었다. 발표에서 보여준 예시는 두 가지다. 주말을 제외하고 매일 09시에 프로파일링을 수집하는 스케줄 설정, 그리고 Grafana 알람에 라벨을 추가해서 알람이 발생하는 순간 프로파일링이 자동으로 트리거되는 설정이다.

### 접근성: 연결 정보를 분석계에 적재

접근성 관점에서는 자주 쓰는 데이터를 분석계에 영속화했다. 누구나 데이터에 접근하고 가공할 수 있게 하기 위해서다. 가장 자주 쓰는 데이터는 연결 정보인데 이슈를 해결하다 보면 서비스와 인프라의 의존 관계를 파악하거나 인프라에 연결된 클라이언트를 특정할 일이 자주 생기기 때문이다.

문제는 어느 한쪽에서만 보면 답이 안 나온다는 점이다. 파드의 통신은 노드를 거쳐 나간다. 그래서 인프라 입장에서 관측되는 연결 주체는 파드가 아니라 노드다. 인프라에서는 파드 정보를 알 수 없고 파드에서는 노드 밖의 연결을 알 수 없다.

<VideoFrame src={podNodeInfra} alt="발표 슬라이드 '2. 자료수집 - 접근성'. Node 상자 안에 Pod 여러 개가 겹쳐 있고 Node에서 Infra 원통으로 화살표가 나간다. 왼쪽에 연결정보의 용도로 서비스와 인프라 맵, 인프라에 연결된 client 특정이 적혀 있다." caption="파드의 통신은 노드를 거쳐 인프라로 나간다. 인프라 쪽에서 보이는 연결 주체는 노드다." time="04:05" videoUrl={videoUrl} />

토스증권은 노드 레벨의 정보를 수집하는 쪽을 택했다. 쿠버네티스의 각 노드에 에이전트를 배포한다. 에이전트가 연결 정보를 보여주는 conntrack 같은 명령어를 실행하고 결과를 DB에 적재한다. 노드 레벨에서 수집했기 때문에 파드, 노드, 인프라까지 통신에 관여하는 모든 IP와 포트를 한 번에 볼 수 있다. 인프라 관점에서 클라이언트를 특정하는 질문과 파드 관점에서 인프라 의존성을 파악하는 질문에 모두 답할 수 있게 됐다. 이 데이터가 분석계에 있으니 쿼리를 어느 정도 할 줄 알면 누구나 가져다 쓸 수 있다.

## 특이점 파악

지금까지 자료를 모은 이유는 특이점을 잘 파악하기 위해서다. 특이점은 문제가 가지는 독자적인 속성을 뜻한다. 특이점이 바로 원인이 되지는 않는다. 대신 조사해야 하는 범위를 줄여 준다.

유저, 서비스, DB로 이루어진 애플리케이션 구성을 가정하면 모든 컴포넌트가 특이점의 후보다. 정점을 보면 특정 사용자, 서비스, DB에 문제가 있을 수 있다. 간선을 보면 특정 호출 구간에서만 문제가 있을 수도 있다.

이 단계의 목표는 한마디로 구체화다. 문제가 어디서 발생하는지 최대한 좁혀 간다. 구체화 방향에 따라 수직과 수평으로 나눈다.

### 수직 구체화

에러가 발생한 서비스 안에 사용자, 배포환경처럼 명확한 계층 구조가 있을 때 쓴다. 토스증권은 정형화된 로그를 쓴다. 로그에 사용자 컨텍스트인 유저 ID와 디바이스 ID, 배포환경 컨텍스트인 파드명, 호스트명, 배포 버전이 같이 기록된다.

에러가 났을 때 이 필드들의 분포를 보면 에러가 특정 값에 몰려 있는지 확인할 수 있고 특정 파드에만 몰려 있으면 노드나 배포 버전은 제외하고 그 파드만 본다. 분포의 편향을 단서로 삼아 넓은 영역에서 좁은 영역으로 조사 범위를 단계적으로 줄인다. 발표에서는 이 흐름을 피라미드 그림으로 보여줬다.

### 수평 구체화

뚜렷한 계층적 특성이 안 보이면 서비스가 공통으로 쓰는 영역을 점검해야 한다. 미들웨어, 네트워크 같은 곳이다. 영역이 너무 많아서 정형화하기 어려운 지점이라고 한다. 원칙은 하나다. 문제가 있는 집단만이 가지는 특성을 찾는다. 예를 들어 앞서 적재한 연결 정보 테이블로 공통 인프라를 확인하거나, 공통 라이브러리가 제공하는 메트릭으로 문제 영역을 좁힌다.

수직, 수평 두 방향으로 구체화를 진행하면 많은 경우 조사 범위를 좁힐 수 있다.

## 가설 생성과 검증

지금까지의 모든 단계는 좋은 가설을 만들기 위한 기반 작업이다. 앞 단계에서 파악한 특이점을 바탕으로, 그 특이점을 유발할 수 있는 요인이 무엇인지를 명제로 만든다. 가설에는 두 가지가 반드시 들어가야 한다.

1. 검증하려는 명제 그 자체
2. 그 명제를 검증하기 위해 필요한 근거와 근거의 수집 방법

가설을 만들었으면 검증한다. 가설이 논리적으로 타당하면 수용, 그렇지 않으면 기각, 판단할 수 없으면 보류한다. 발표자는 이 과정이 테스트 코드를 짜는 것과 아주 비슷하다고 했다. 가설에 따라 예측되는 값을 정의하고 실측값을 확보하고 둘을 비교한다. 실측 데이터는 테스트 환경에서 동일한 이슈를 재현해서 얻는다. 재현이 어려우면 원인으로 의심되는 부분을 제거하고 추이를 관찰하는 방법도 쓴다.

## 사례: Redis conntrack 테이블 포화

2026년 어느 날 서비스에서 에러가 발생했다. 앞서 만든 알람 시스템 덕분에 최근 배포 이력, 작업 이력, 에러 통계에 특이사항이 없다는 건 바로 확인됐다.

### 1회차

특이점 파악을 위해 가장 기본인 로그 메트릭부터 봤는데 사용자나 배포환경 쪽의 특이점은 없었다. 대신 로그를 남긴 소스를 보니 세 가지가 눈에 띄었다. 대부분의 로그가 Redis 관련 클래스에서 찍혔다. 내용은 대부분 Redis connection timeout. 그리고 대상 Redis가 하나였다.

더 구체화하기 위해 해당 Redis 노드의 node exporter 메트릭과 커널 로그를 확인했다. nf_conntrack 테이블이 가득 찼다는 메트릭과 로그가 있었다. 리미트가 260k로 작지 않은 값인데도 가득 찬 것이다.

<VideoFrame src={nfConntrackFull} alt="발표 슬라이드 '사례, 특이점 파악 - 1회차'. NF Conntrack 그래프에서 Current 값이 09:00 무렵 급격히 올라 Max 점선에 붙어 있다. 아래에 커널 로그 nf_conntrack: table full, dropping packet 이 있다." caption="node exporter 의 NF Conntrack 그래프가 Max 에 붙어 있다. 아래 커널 로그에 table full, dropping packet 이 찍혔다." time="08:55" videoUrl={videoUrl} />

conntrack은 connection tracking의 줄임말로 커널이 관리하는 연결 장부라고 생각하면 된다. 이 테이블이 가득 차면 커널은 신규 커넥션을 받지 못하고 패킷을 드랍해서 클라이언트 입장에서는 connection timeout이 난다. 그래서 Redis의 conntrack 테이블을 특이점으로 봤다.

첫 가설은 "원인이 애플리케이션과 상관없는 인프라에 있다"였다. 근거는 두 가지였다. 최근 애플리케이션 배포가 없었고 Redis 클러스터의 한 노드에서만 conntrack이 가득 찼다. 이 가설을 검증하는 데 필요한 데이터는 자연스럽게 "Redis 노드에 애플리케이션 외의 커넥션이 많은가"가 됐다.

먼저 Redis에 연결된 클라이언트들의 IP와 포트 목록을 확보해서 자료 수집 단계에서 적재해 둔 연결 정보의 NAT IP와 포트에 매칭했다. 연결 정보 테이블에서 찾을 수 있으면 애플리케이션의 연결이고 없으면 의심하던 제3의 연결이다. 데이터가 이미 분석계에 있었기 때문에 쿼리 하나로 매칭 결과를 볼 수 있었다.

결과는 기각. 애플리케이션이 아닌 곳에서 온 연결은 유의미하게 많지 않았다. 오히려 80% 이상의 연결이 애플리케이션에서 왔다.

### 2회차

가설이 기각됐으니 다음 사이클의 첫 단계인 자료 수집으로 돌아갔다. 다만 1회차에서 얻은 것이 있다. 애플리케이션에서 온 연결이 conntrack 테이블의 80% 이상을 차지한다는 사실이다. 탐색 범위를 애플리케이션으로 좁혀 주는 단서였다.

애플리케이션과 Redis 사이의 통신 구간에서 커넥션이 어떻게 쓰이는지 보기 위해 tcpdump를 수행했고 conntrack 테이블 크기의 트렌드를 보니 증가 패턴에 주기성이 있었다. 그래서 자료 수집 단계에서 말한 스케줄 기반 수집을 그대로 쓸 수 있었다.

tcpdump를 분석하니 대부분의 요청은 이미 맺어진 커넥션을 쓰고 있었다. 하지만 일부는 커넥션을 신규로 맺고 끊는 모습이 보였다. 덤프에서 SYN 패킷으로 신규 커넥션을 만들고 Redis와 인증 정보를 교환하고 필요한 요청을 처리한 다음 연결을 닫는 흐름이 그대로 보였다.

여기서 두 번째 가설을 세웠다. "애플리케이션이 커넥션을 온디맨드로 생성한다." 커넥션이 생성되는 속도가 정리되는 속도보다 빠르면 테이블이 가득 찬다. 이 가설에 필요한 데이터는 애플리케이션에서 커넥션을 신규로 만드는 로직이다. 코드를 보니 의심 가는 지점이 나왔다. Spring이 Redis 통신을 추상화하기 위해 제공하는 RedisTemplate의 일부인데, Redis pipeline을 쓰면 이 로직을 탄다. getConnection에서 신규 커넥션을 만들고 로직이 끝나면 releaseConnection으로 종료한다.

<VideoFrame src={redisTemplateCode} alt="발표 슬라이드 '사례, 가설 검증 - 2회차'. 근거 수집으로 코드 레벨에서 의심 가는 지점 확인이라고 적혀 있고 아래에 RedisTemplate의 execute 메서드 Java 코드가 있다. getConnection 호출에 신규 커넥션 생성 주석, finally 블록의 releaseConnection 호출에 커넥션 close 주석이 달려 있다." caption="RedisTemplate 의 execute 메서드. getConnection 에서 커넥션을 만들고 finally 의 releaseConnection 에서 닫는다." time="12:06" videoUrl={videoUrl} />

검증은 두 관점에서 했다.

1. 재현 관점. Redis pipeline을 쓰는 API를 테스트 환경에서 실행해서 신규 커넥션이 생성되고 종료되는지 확인한다.
2. 원인 제거 관점. pipeline 로직을 제거한 뒤 conntrack 테이블 크기가 안정화되는지 관찰한다.

결과는 둘 다 가설을 뒷받침했다. 테스트 환경에서 문제 API를 실행하자 tcpdump에서 커넥션이 매번 신규로 생성되고 종료되는 게 확인됐는데 자료 수집 단계에서 관측한 것과 같은 패턴이 재현된 것이다. pipeline 로직을 제거한 뒤에는 conntrack 테이블 크기가 80K 수준에서 1.7K 수준으로 떨어져 안정화됐다. 재현과 원인 제거 후 정상화, 두 근거를 확보했기 때문에 가설을 수용하고 이슈를 종결했다.

### 사후 점검

문제가 해결된 뒤에는 재발 가능성을 검토한다. 유사한 컴포넌트에서도 같은 문제가 생길 여지가 있는지 보는 과정이다. 다른 서비스들의 pipeline 사용 패턴을 조사했고 문제가 없음을 확인했다.

또 하나 발견한 게 있다. conntrack 사용률에 알람이 없었다. 그래서 서비스에서 에러가 나고 나서야 문제를 인지한, 발표자 말로는 다소 아쉬운 케이스였다. 인지 방식 측면에서 conntrack 사용률 알람도 추가해 뒀다고 한다.

## 발표자의 소감

SRE 팀에서 일하면 이런 트러블슈팅을 할 기회가 많다고 한다. 발표자가 그 과정에서 느낀 세 가지로 발표를 마쳤다.

첫째, 문제를 빠르게 인지하는 게 첫걸음이다. 문제가 있는지조차 모르면 아무것도 할 수 없다.

둘째, 특이점 파악만 잘되면 대부분 해결된다. 이슈를 해결할 때 가장 어려운 것 중 하나가 봐야 하는 구간과 그렇지 않은 구간을 나누는 일인데 특이점을 잘 잡아 두면 이 분류에 큰 도움이 된다.

셋째, 첫 번째 사이클을 빠르게 돌리는 게 중요하다. 사례에서도 첫 가설을 검증하는 과정에서 나온 데이터가 두 번째 가설을 세우는 데 크게 기여했다. 막혀 있다면 가설이 조금 마음에 들지 않아도 일단 검증해 보는 것도 좋은 방법이다.

## 내 생각

가설에 검증 방법을 같이 적게 한 부분이 기억에 남는다. 명제만 세우면 그 다음에 뭘 봐야 할지 다시 고민해야 하는데, 가설을 만들 때부터 어떤 근거를 어떻게 모을지 정해 두니 검증이 테스트 코드처럼 돌아간다. 첫 가설이 틀렸는데도 그 검증에서 나온 80%라는 숫자가 두 번째 가설의 출발점이 된 것도 그래서 가능했던 것 같다.

연결 정보를 노드 레벨에서 미리 모아 둔 것도 그렇다. 사례에서 Redis 클라이언트 목록을 매칭하는 데 쿼리 하나로 끝났는데, 장애가 나기 전에 자료 수집을 자동화해 둔 덕분이다. 장애 대응 속도는 평소에 뭘 쌓아 뒀는지에서 갈리는 것 같다.
