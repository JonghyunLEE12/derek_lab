한국에서 시술을 받고 싶은 외국인은 병원에 한국어로 전화 문의를 하기 어렵다. 그래서 외국인이 원하는 시술을 말하면 AI가 병원 여러 곳에 한국어로 전화를 걸어 가격과 예약 가능 날짜를 물어보고, 병원별 결과를 정리해서 돌려주는 서비스를 생각했다. 최종 목표는 실제 출시이고 그 전에 POC로 가능성을 확인한다. 회사가 외국인환자 유치업으로 등록되어 있어서 서비스가 병원을 골라 연결해 주는 구조가 가능하다.

참고한 유사 서비스는 범용 AI 비서 앱 피클이다. 전화 대행 기능이 있지만 외국인이나 의료 시술에 특화되어 있지는 않다.

지난번 <a href={prevPost}>다국어 AI 음성 상담 PoC</a>는 외국인 고객과 AI가 외국어로 통화하는 쪽이었다. 이번에는 방향이 반대다. 외국인의 요청을 받은 AI가 한국어로 병원 직원과 통화한다. 이 글은 그 POC 1부의 기록이다.

## POC가 답할 질문과 범위

질문은 하나다. AI가 병원 접수 직원과 한국어로 통화해서 시술 가격과 예약 가능 날짜를 실제로 받아낼 수 있는가.

범위를 먼저 적어 둔다. 이번 1부에는 실제 전화 발신이 없다. 전화 회선 대신 브라우저 마이크를 전화 음질(8kHz μ-law)로 낮춰 연결하는 비교 도구를 만들었고, 그걸로 음성 구성을 쟀다. 측정에 쓴 병원 직원 음성도 사람이 아니라 미리 합성한 음성이다. 결과는 그 범위 안에서만 읽어야 한다.

POC 전체에서 하지 않기로 한 것은 이렇다.

- 예약 확정, 결제
- 실제 병원으로의 발신. 내 전화번호로 걸고 내가 병원 접수 직원 역할을 한다
- 실제 외국인 고객 응대, 공개 배포, 개인정보 수집 동의, 결과 알림
- 병원 자동 추천. 가상의 병원 몇 곳을 수동으로 등록하고 전화번호는 모두 내 번호로 둔다
- 모바일 앱. API만 앱에서 쓸 수 있게 분리한다

반대로 이렇게 되면 실패라고 정해 둔 것도 있다.

- AI가 의료 조언을 하거나 예약을 확정해 버리는 것
- 잘못된 가격이나 날짜가 검수 없이 외국인에게 전달되는 것
- 법률 검토 없이 실제 병원에 AI 고지를 끈 채로 통화하는 것
- 병원이 원치 않는 반복 전화로 제휴 관계가 상하는 것
- POC 중에 등록된 번호가 아닌 곳으로 전화가 나가는 것

## 가장 중요한 것은 사람처럼 들리는 통화

최우선으로 둔 것은 병원 직원이 전화를 받았을 때 목소리와 대화 흐름이 실제 사람처럼 느껴지는 것이다. 다른 기능보다 이것을 먼저 검증하기로 했다.

지난 PoC에서 가져온 교훈이 출발점이다.

- 응답 지연이 가장 큰 벽이었다. 목표 1.5초에 실측 3.0초에서 5.4초였고 LLM 첫 토큰과 STT가 대부분을 차지했다
- 음성 품질보다 STT 오류와 LLM의 도구 호출 누락이 상담 성공을 더 크게 좌우했다
- 품질이 좋은 TTS는 실시간이 안 됐다. 실시간이 되는 것은 Kokoro와 Qwen3-TTS였다
- 끼어들면 바로 재생을 멈추는 것, 처리 중 안내음을 먼저 트는 것, 숫자와 코드를 읽기 쉽게 바꾸는 문장 단위 정규화는 효과가 있었다
- Smart Turn은 끝난 발화를 미완료로 잘못 판정해 1.5초를 버린 적이 있다
- 지난 실험에는 한국어, 전화 회선, 맞장구가 없었다. 이번에 새로 봐야 한다

이번 POC에서 "사람처럼"은 여섯 가지로 풀었다.

| 요소 | 기준 |
| --- | --- |
| 목소리 | 한국어가 자연스럽고 전화 음질(8kHz 협대역)로 낮춰도 기계음이 드러나지 않을 것 |
| 응답 속도 | 상대 말이 끝난 뒤 첫 소리까지 중앙값 1초 이내, 최대 1.5초 |
| 말 주고받기 | 끼어들면 즉시 멈춤, 말이 끝났는지 판단, 짧은 맞장구, 생각하는 동안 "잠시만요"로 빈 시간 메우기 |
| 말투 | 전화 통화체 존댓말, 짧은 문장. 글을 읽는 느낌이 나지 않을 것 |
| 숫자 읽기 | 가격("삼십오만 원"), 날짜, 횟수를 한국어 방식으로 읽을 것 |
| 되묻기 | 가격과 날짜는 들은 내용을 한 번 되읽어 확인. 지난 실험에서 STT 오류가 실패의 주원인이었기 때문이다 |

## 흐름

POC에서는 아래 흐름의 외국인을 직원이, 병원을 내 전화가 대신한다. 흐름 자체는 출시 때와 같게 만든다.

1. 외국인이 웹 폼에 자기 언어로 시술, 시술 세부 정보(부위, 횟수 등), 희망 시기를 입력한다
2. 서버가 시술에 맞는 병원을 등록된 목록에서 고르고 병원별 통화 작업을 대기열에 올린다
3. AI가 병원에 전화한다. 회사명을 밝히고 외국인 고객을 대신해 가격과 예약 가능 날짜를 문의한다고 말한다
4. 통화가 끝나면 통화 기록을 글로 바꾸고 가격, 예약 가능 날짜, 조건(내원 상담 후 확정, 부가세 포함 여부 등)을 구조화한다
5. 직원이 구조화된 결과를 통화 기록과 대조해 확인한다
6. 확인된 결과가 병원별 비교표로 외국인의 언어로 웹에 표시된다

## 통화 규칙

AI가 통화 중에 지켜야 할 규칙은 이렇게 정했다.

- 통화 시작 시 회사명과 문의 목적을 밝힌다
- 의료 조언이나 시술 추천을 하지 않는다
- 예약을 확정하지 않는다. 병원이 예약을 잡으려 하면 고객 확인 후 다시 연락하겠다고 답한다
- 고객 정보는 문의에 필요한 것(국적, 희망 시술, 폼에 입력된 시술 세부 정보, 희망 시기)만 말한다
- 병원이 고객 이름이나 연락처를 물으면 문의 단계라 알려드릴 수 없다고 답한다
- 폼에 없는 정보를 병원이 물으면 지어내지 않고 확인 후 다시 연락하겠다고 답한 뒤 그 질문을 결과에 기록한다
- 병원이 답을 거절하거나 통화를 끝내려 하면 정중히 종료한다
- ARS 안내가 나오면 버튼 입력으로 상담 연결을 시도하고 연결되지 않으면 실패로 기록한다
- 같은 병원에 하루에 정해진 횟수 이상 재시도하지 않는다
- 병원 운영 시간에만 발신한다

AI 고지와 녹음 안내는 설정값(`DISCLOSE_AI`, `ANNOUNCE_RECORDING`)으로 켜고 끌 수 있게 만들었다. POC 통화는 내 번호로만 나가서 제3자가 듣지 않기 때문에 POC 설정에서는 둘 다 껐다. 고지를 끈 상태에서도 상대가 사람인지 AI인지 직접 물으면 사람이라고 거짓말하지 않는다. 실제 병원에 발신하기 전에는 다시 정해야 한다. AI 기본법 제31조의 사전 고지 의무와 통화 녹음 요건이 걸려 있어 법률 검토가 필요하고, 그때까지 고지를 끈 상태로는 허용 목록 밖의 번호로 발신하지 않는다.

## 서버 구성

서버는 Rust로 정했다. 전화 음성을 주고받는 아랫단(SIP 연결, 음성 패킷 처리)은 직접 만들지 않고 FreeSWITCH 같은 기존 전화 서버를 앞에 둔다.

| 부분 | 구성 | 비고 |
| --- | --- | --- |
| 서버 | Rust (axum, tokio) | 요청 접수와 결과 조회를 HTTP API로 분리해 앱에서도 쓴다 |
| 전화 | 국내 070 SIP 사업자와 기존 전화 서버 | 독립 모듈로 분리. 번호나 통신사를 바꿀 때 이 모듈과 설정만 바꾼다 |
| 음성 AI | 교체 가능한 모듈 | 비교 결과로 구성을 정한다 |
| 결과 정리 | 통화 기록을 LLM으로 구조화하고 번역 | 추출 항목마다 근거가 된 통화 구간을 같이 저장 |
| 저장 | SQLite | 요청, 병원, 통화, 통화 기록, 추출 결과, 검수 상태 |
| 웹 | 입력 폼, 결과 페이지, 직원용 검수 페이지 | 최소한의 화면 |

1부에서 만든 것은 전화 회선 없이도 돌아가는 부분이다. 음성과 전화는 trait 뒤에 두었다. 구현한 순서는 이렇다.

- 프로젝트 뼈대, 도메인 타입, SQLite 저장소
- 가격, 날짜, 횟수의 한국어 읽기 정규화
- 발신 가드. 허용 목록, 운영 시간, 재시도 제한
- 통화 지시문과 첫 발화. 고지와 녹음 안내 설정 포함
- 음성 세션 인터페이스, 전화 음질 변환, 지연 기록
- 통화 기록에서 결과를 추출하고 근거를 검증하는 단계
- 문의 API와 결과, 검수 화면
- 로컬 한국어 스트리밍 음성 세션과 전화 음질 웹 벤치

만든 뒤에 고친 것들도 대부분 잘못된 정보가 나가는 걸 막는 쪽이었다.

- 추출한 가격을 근거 구간의 금액과 대조한다
- 번역된 요약에서 검증되지 않은 금액을 표시한다
- 검수 승인에는 검토한 버전을 같이 보내야 한다
- 검수 API는 직원 토큰으로 막고 문의 id는 추측할 수 없는 값으로 만든다
- 통화 지시문을 만들기 전에 연락처 정보를 지운다
- 재시도는 통화 건 단위로 세고 번호별 하루 발신 수에도 상한을 둔다
- 발신 시도는 별도 테이블에 기록한다

발신 가드의 허용 목록은 POC에서 내 번호 하나다.

## 음성 후보

음성 구성은 두 방식을 후보로 뒀다.

- 방식 A는 실시간 음성 대화 모델 하나가 듣기와 말하기를 모두 처리한다. 지연이 짧고 맞장구와 끼어들기가 자연스럽다
- 방식 B는 STT, LLM, TTS를 스트리밍으로 이어 붙인다. 목소리와 각 단계를 자유롭게 고를 수 있지만 지연 관리가 어렵다. 지난 실험이 이 방식이다

회사 프로젝트라서 유료 API도 후보에 넣고 조사했다. 아래는 공식 문서를 요약 도구로 읽은 결과다. 모델 이름, 파라미터, 가격은 구현 전에 원문으로 다시 확인해야 하고 3분 통화 비용은 공식 단가로 계산한 추정치다. 지연과 한국어 음질은 어느 문서에도 비교할 수 있는 수치가 없어서 직접 재야 한다.

| 방식 | 후보 | 한국어 | 8kHz μ-law | 3분 비용 |
| --- | --- | --- | --- | --- |
| A | OpenAI `gpt-live-1` | 지원 언어 목록 확인 못함 | 직접 지원 | 약 $0.15와 별도 모델 사용료 |
| A | Google `gemini-3.8-live` | 지원 목록에 `ko` | 미지원. 입력 16kHz, 출력 24kHz PCM | 약 $0.04에서 0.07 |
| B TTS | ElevenLabs `eleven_v4_turbo` | 명시 | `ulaw_8000` | 약 $0.024 |
| B TTS | 로컬 Qwen3-TTS-12Hz-1.7B | 한국어 화자 있음 | 로컬 변환 | 무료 |
| B STT | 리턴제로 `sommers_ko` | 한국어 전용 | MULAW 8000Hz | 약 50원 |

지난 실험의 Kokoro-82M은 한국어를 지원하지 않아 뺐다. VoxCPM2와 CosyVoice3는 한국어를 지원하지만 지난 실험에서 실시간이 되지 않아 1차 비교에서 뺐다.

이번 구현에서는 유료 API 없이 방식 B의 로컬 구성만 비교했다. 방식 A는 아직 구현하지 않았다.

## 로컬 구성 네 개로 20통화

조건은 이렇다. M4 Pro, 통합 메모리 48GB다. STT는 MLX Whisper large-v3-turbo, TTS는 Qwen3-TTS-12Hz-1.7B-Base-bf16, LLM은 Ollama Qwen3.5 2B 또는 4B다. LLM 설정은 `think:false`, `temperature:0`, `num_ctx:4096`, `num_predict:180`이다. 에이전트 목소리는 FLEURS 한국어 테스트의 공개 참조 음성 여성과 남성 둘이다. LLM 두 개에 목소리 두 개를 곱해 구성이 네 개다.

직원 대본은 다섯 개다. 바로 답변, 조건 되묻기, 내원 상담 유도, 답변 거절, 예약 유도다. 대본마다 독립 세션에 넣어 구성당 5통화, 합쳐서 20통화를 돌렸다. 직원 음성은 미리 합성한 8kHz WAV이고 실제 사람이 말한 데이터나 실제 전화 회선이 아니다. 모델은 STT 하나, TTS 하나, LLM 하나만 올렸고 2B에서 4B로 바꿀 때는 2B를 내렸다.

지연은 세 구간으로 나눠 기록했다. 듣기는 마지막 유성 프레임 뒤 400ms 종료 감지와 STT 처리 시간이다. 생각은 LLM 첫 토큰 또는 먼저 나온 메움 발화까지다. 말하기는 첫 토큰 뒤 첫 답변 PCM까지다. 메움 발화는 "네, 잠시만요" 같은 짧은 말을 세션 준비 때 미리 합성해 두고 응답이 느린 턴에 먼저 트는 것이다. 측정 종점은 세션이 첫 PCM을 만든 시점이라 브라우저 재생 시작이나 전화망 지연은 들어 있지 않다.

단위는 ms다. 목표는 첫 소리 중앙값 1000 이하, 최대 1500 이하다.

듣기 약 1.0초 중 400ms는 턴 종료 감지이고 나머지 약 0.6초가 Whisper 처리다. 여기에 2B 약 0.4초, 4B 약 0.95초에서 0.99초의 첫 토큰 대기와 문장 완성, TTS 지연이 더해진다.

## 규칙을 얼마나 지켰나

저장된 에이전트 전사를 사람이 읽는 기준으로 검토했다. 목소리를 여성에서 남성으로 바꿔도 같은 LLM의 문장 내용은 바뀌지 않았다. 아래 횟수는 구성별 답변 5개 중 명시적인 사례 수이고 자동 판정은 아니다.

| 구성 | 근거 없는 의료 설명 | 예약 확정 | 없는 사실이나 조건 추가 | 관찰 |
| --- | ---: | ---: | ---: | --- |
| 2B 여성 | 1/5 | 1/5 | 2/5 이상 | 조건 질문에 부위와 가격을 지어냄. 예약 유도에 확정 |
| 2B 남성 | 1/5 | 1/5 | 2/5 이상 | 여성 구성과 같은 문장 |
| 4B 여성 | 0/5 | 0/5 | 1/5 이상 | 예약은 거절했지만 상담 조건 추가와 역할 혼동이 남음 |
| 4B 남성 | 0/5 | 0/5 | 1/5 이상 | 여성 구성과 같은 문장 |

2B는 실패 조건으로 적어 둔 두 가지를 그대로 했다. 조건 질문에 "입술과 눈동자 주변에 주로 사용"이라는 의료 설명과 "1cc가 삼십만 원"이라는 가격을 지어냈고, 예약 유도에는 "예약을 잡겠습니다"라고 확정했다. 거절 응답에서는 "연락이 닿지 못했습니다"처럼 실제 대화와 맞지 않는 말도 했다.

4B는 예약 확정과 의료 설명은 없었지만 깨끗하지는 않았다. 내원 상담 응답에서 직원은 가격만 말했는데 에이전트는 날짜에도 내원 상담 조건을 붙였다. 조건 질문에서는 문의를 대신하는 쪽인데 병원 직원처럼 가격을 안내하는 역할 혼동이 있었다. 두 LLM 모두 일부 답변이 세 문장 이상이라 한두 문장 규칙도 어겼다.

프롬프트만으로는 규칙 준수가 보장되지 않았다. 역할을 더 명확히 하는 프롬프트 실험, 생성 뒤 규칙 검사, 정해진 예약 거절 문장 적용을 따로 검증해야 한다.

## 한국어 STT와 TTS에서 본 것

20통화의 인식문에서 가격 35만 원과 50만 원, 보톡스와 필러, 다음 주 화요일과 오후 2시는 모두 남았다. 주요 정보 검사는 구성당 10/10, 합계 40/40이다. 다만 이건 내가 고른 합성 입력의 정보 보존 검사다. 전체 WER이나 실제 사람 발화 인식률이 아니다.

Whisper는 "삼십오만 원"을 `35만 원`, "오후 두 시"를 `오후 2시`, "씨씨"를 `cc`로 적었다. 의미상 오인식은 아니고 금액은 TTS 직전에 한국어 읽기로 다시 바꾼다.

처음에는 직원 말의 앞부분이 사라지는 문제가 있었다. 바로 답변 대본에서 가격 부분이 통째로 빠지고 "부가세 포함이고 다음 주 화요일 오후 2시 가능합니다"만 남았다. Whisper 정확도 문제로 단정하지 않고 VAD와 취소 경로를 고쳤다. RMS 문턱을 300에서 120으로 낮추고, 앞부분 160ms를 보존하고, 취소된 STT의 입력을 다음 인식에 병합하고, 이미 인식된 상대 발화를 유지하게 했다. 고친 뒤 20통화에서는 같은 누락이 없었다.

출력 음량도 낮았다. 에이전트 채널 RMS 중앙값이 여성 0.018, 남성 0.013 수준이었다. 자연스러움, 성별 인상, 숫자 발음의 청취 정확도는 사람이 아직 평가하지 않았다. 파형이 만들어지고 전사가 맞다는 것만으로 사람이 듣기에 자연스럽다고 판단하지 않는다.

## 실제 마이크를 붙였을 때

합성 입력으로는 돌아가던 것이 실제 마이크에서는 소리가 사라졌다. 원인은 브라우저, 벤치, 음성 세션 세 곳에 있던 RMS 120 즉시 취소였다. 주변 소음만으로 끼어들기가 걸려 재생이 지워졌다.

고친 내용은 이렇다.

- 서버 VAD가 확정한 끼어들기 이벤트만 재생을 지운다
- 처음 500ms와 무음 구간에서 소음 바닥을 추정하고 AI가 말하는 중에는 더 높은 문턱을 쓴다
- 발화 시작 판정에는 연속 200ms가 필요하다. 약한 첫 음절이 끊겨 들어와도 버리지 않게 후보 구간을 보존한다
- 출력은 100ms PCM 단위로 목표 RMS 0.08에 맞추고 피크를 0.9 이하로 제한한다
- 벤치 페이지에 입력 레벨, VAD 상태, 소음 바닥, 문턱, 끼어들기 끄기, 출력 음량을 표시한다

확인은 직원 음성에 RMS 300 백색 잡음을 섞어 20ms씩 보내는 테스트로 했다. 첫 인사 12.40초와 메움 포함 답변 14.32초가 끝까지 나갔고 끼어들기 오검출은 0회였다. 출력 채널 RMS는 0.0804가 됐다.

다 풀린 건 아니다. 같은 테스트에서 "부가세 포함"을 "보관세포안"으로 잘못 인식했고 LLM도 그대로 잘못 되읽었다. 첫 소리 지연은 2614ms로 여전히 목표 미달이다. 실제 마이크 청취와 스피커 에코는 아직 검증하지 않았다. 에너지 기반 VAD라서 지속적인 큰 잡음이나 에코를 사람 목소리와 구분하지 못할 수 있다.

## 알게 된 것

지난 PoC에서 본 것이 한국어에서도 반복됐다. 응답 지연이 목표를 넘겼고 그 대부분은 TTS가 아니라 듣기와 LLM 쪽에 있었다. 이번에는 듣기 구간만 약 1.0초라 이것 하나로 목표 중앙값을 다 쓴다.

모델 크기와 규칙 준수는 같이 움직였다. 2B는 첫 토큰이 약 0.4초로 빨랐지만 예약을 확정하고 가격을 지어냈다. 4B는 그 두 가지는 하지 않았지만 첫 토큰이 약 0.95초였다. 모델만 줄이면 지연은 줄어도 규칙 준수가 나빠질 수 있어서 지연과 사실성을 같이 봐야 한다.

합성 입력에서 통과한 것이 실제 마이크에서는 깨졌다. 조용한 합성 음성 20통화에서 주요 정보가 다 남았어도 소음을 섞자 "부가세 포함"이 틀렸다.

## 한계와 다음에 할 것

남은 한계는 이렇다.

1. 사람의 청취 평가를 아직 하지 않았다. 최우선이라고 정한 사람 같은 정도는 측정된 게 없다
2. 어느 구성도 지연 목표를 달성하지 못했다. 음성 구성은 아직 정하지 않았다
3. 프롬프트만으로 통화 규칙이 지켜지지 않는다
4. 직원 음성이 합성이고 실제 전화 회선을 타지 않았다. 사람의 작은 목소리, 잡음, 겹침, 억양, 시술명 변형에 대한 결과가 없다
5. 유료 API와 방식 A는 조사만 했고 재지 않았다

다음에 볼 것은 이렇다.

1. 증분 STT 또는 더 작은 한국어 STT를 비교한다. 발화 완결 여부를 유지하면서 400ms 종료 대기를 줄인다
2. 첫 문장 길이 제한, 짧은 확인 응답의 캐시, TTS 참조 인코딩 재사용을 실측한다
3. 역할을 명확히 하는 프롬프트, 생성 뒤 규칙 검사, 정해진 예약 거절 문장을 검증한다
4. 후보 이름을 가린 녹음으로 청취 평가를 한다. 사람 같은 정도 1점에서 5점, 어색한 멈춤, 숫자와 시술명 발음, 말 끊기 반응, 음량을 나 포함 2명 이상이 기록한다
5. 2부에서 FreeSWITCH와 070 회선을 연결하고 통화 대기열을 실행해 내 번호로 30건을 테스트한다. 070 회선 계약과 음성 구성 결정이 끝난 뒤에 계획한다

내 번호로 거는 테스트로는 알 수 없는 것도 있다. 실제 병원의 수신율, 그리고 "가격은 내원 상담 후 안내" 같은 답이 실제로 얼마나 나오는지다. 이 둘은 POC 다음 단계인 제휴 병원 실통화에서 확인한다.
