"ThreeRT 기술"을 웹검색해 달라는 말로 시작했다. 그런 이름의 기술은 없었고, 비슷한 이름 중에 three.js에서 실시간 레이트레이싱 조명을 켜 주는 라이브러리 **three-realtime-rt**가 눈에 들어왔다. 그래서 이걸로 신주쿠 가부키초 거리를 웹사이트로 만들 수 있냐고 물었다. 참고 이미지로는 歌舞伎町一番街 빨간 게이트 사진 한 장을 줬고, 요구는 "최대한 그럴싸하게, 네온사인이 풍부하게"였다.

결과물은 아래 주소에서 바로 볼 수 있다. 접속이 없으면 서버가 멈춰 있어서 첫 접속은 몇 초 걸린다. WebGL2가 되는 데스크톱 브라우저를 권장한다.

범위를 먼저 적어 둔다. 나는 코드를 직접 쓰지 않았다. 요청을 몇 줄 쓰고, 중간에 "실제로 걸어 다닐 수 있게"를 추가했다. 이 글의 숫자는 작업 기록과 결과물의 README에서 가져온 것이다. 오전 10시쯤 검색을 시작해서 11시 전에 배포 주소를 받았다.

## three-realtime-rt가 하는 일

이름 그대로 three.js 장면에 레이트레이싱 조명을 켜 주는 라이브러리다. MIT 라이선스이고 이번에 쓴 버전은 0.16.7이다.

방식은 하이브리드다. 화면에 무엇이 보이는지는 평소처럼 래스터화로 그리고, 조명만 BVH(광선이 부딪히는 물체를 빨리 찾는 트리 구조)를 상대로 광선을 쏴서 계산한다. 그래서 부드러운 그림자, 1회 반사 간접 조명(GI), 금속 표면 반사, 유리 굴절, 빛줄기 같은 효과가 나온다. RT 코어를 쓰지 않고 셰이더 계산으로 돌아가서 WebGL2만 되면 동작한다.

적용은 짧다. 원래 `renderer.render(scene, camera)`를 부르던 자리에 이렇게 바꾸면 된다.

```js
const rt = new RealtimeRaytracer(renderer);
rt.compileScene(scene);
// 매 프레임
rt.render(scene, camera);
```

같은 장면에서 레이트레이싱을 끄면 이렇게 보인다. 페이지 왼쪽 아래 버튼으로 직접 켜고 끌 수 있다.

<img src={`${base}/images/blog/kabukicho-rt/rt_off.jpg`} alt="레이트레이싱을 끈 같은 장면. 바닥과 건물이 어둡고 반사가 거의 없다" />

간판 자체는 똑같이 빛나지만, 그 빛이 바닥과 벽에 번지고 비치는 건 레이트레이싱을 켰을 때만 나온다.

## 라이브러리 제약을 먼저 읽었다

구현을 맡기기 전에 Claude가 패키지를 받아 README와 타입 정의를 먼저 읽었다. 네온 거리를 만들려면 걸리는 제약이 몇 개 있었다.

| 제약 | 어떻게 피했나 |
| --- | --- |
| 스스로 빛나는 메시는 진짜 면광원이 되지만, 전체 삼각형 256개까지만 | 게이트와 큰 간판 몇 개만 면광원으로 쓰고, 나머지 간판은 `rtNoAreaLight`로 화면에서만 빛나게 했다. 벽과 바닥에 번지는 색은 간판 앞에 둔 점광원 132개로 만들었다 |
| `InstancedMesh`는 한 개로 뭉개진다 | 쓰지 않고 같은 재질끼리 지오메트리를 합쳤다 |
| `Line`, `Sprite`, `Points`는 레이트레이싱에서 숨겨진다 | 전선을 얇은 원기둥으로 만들었다 |
| 반사는 금속성(metalness)이 있는 표면에만 생긴다 | 젖은 아스팔트에 금속성을 주고 웅덩이 부분은 거칠기를 낮췄다 |
| 발광 세기를 바꾸면 조명 계산에는 다시 컴파일하기 전까지 반영되지 않는다 | 네온 깜빡임은 재질 밝기와 옆 점광원 세기를 같이 바꾸는 방식으로 했다 |

이 표를 그대로 작업 명세에 넣었다. 최종 장면은 정적 삼각형 140,968개, 움직이는 삼각형 11,538개, 점광원 132개, 면광원 삼각형 38개다.

## 장면은 전부 코드로 만들었다

사진이나 3D 모델 파일은 하나도 쓰지 않았다. 건물, 간판, 간판 글씨 텍스처, 바닥 질감까지 브라우저에서 생성한다.

- 게이트에서 시작해 거리 양쪽에 건물 30채가 있고, 옆 골목 2개에도 들어갈 수 있다.
- 세로 간판, 가로 빌보드, 1층 가게 불빛, 빨간 초롱, 자판기, 진입금지 표지가 있다.
- 간판 글씨는 カラオケ, 焼肉, 居酒屋, 案内所 같은 일반 단어만 썼다. 실제 상호나 로고는 넣지 않았다.
- 사람 24명이 걸어 다닌다. 단순한 로우폴리 형태이고, 움직이는 BVH 갱신이 평균 3ms를 넘으면 멈추게 했다.

## 중간에 "걸어 다닐 수 있게"를 추가했다

처음 명세에도 앞뒤로 이동하는 기능은 있었는데, 작업 도중에 1인칭으로 실제로 걸어 다니게 해 달라고 다시 요청했다. 지금은 이렇게 움직인다.

- **PC:** 화면을 클릭하면 마우스로 시점이 돌아간다. WASD나 방향키로 걷고 Shift로 뛴다. Esc를 누르면 마우스가 풀린다.
- **모바일:** 왼쪽 아래 조이스틱으로 걷고 오른쪽을 드래그해서 둘러본다.
- 건물과 기둥은 통과하지 못하고 벽을 따라 미끄러진다.
- 오른쪽 아래 미니맵에 위치와 방향이 나오고 Gate, Mid, End 버튼으로 순간이동할 수 있다.

## 젖은 바닥 반사를 한 번 고쳤다

첫 결과물을 스크린샷으로 확인하니 웅덩이에 비친 간판이 부드럽게 늘어지지 않고 네모난 계단 모양 줄무늬로 깨져 있었다. 게이트 앞 바닥에는 검은 얼룩도 하나 있었다.

원인은 구현 워커가 라이브러리 반사 위에 추가한 화면 공간 반사(SSR) 패스였다. 광선을 진행하는 간격이 거리에 비례해 커지는데 보정은 4번뿐이라 반사된 글씨가 띄엄띄엄 끊겼다. 진행 시작점을 픽셀마다 무작위로 흔들고, 보정을 7번으로 늘리고, 프레임 사이에 누적하고, 세로 방향으로 빛을 번지게 해서 고쳤다. 이 패스에 드는 시간은 0.47~1.11ms로 측정됐다.

레이트레이싱 라이브러리 자체의 반사는 조명 해상도가 낮아서 가까이 있는 간판 글씨까지 선명하게 비추지는 못한다. 그래서 화면에 보이는 간판은 SSR로 선명하게 비추고, 화면 밖 색은 라이브러리 반사가 채우는 구조가 됐다.

## 역할은 이렇게 나눴다

내 환경에는 Orca 워커 오케스트레이션이 붙어 있다. 이번에는 이렇게 돌렸다.

| 역할 | 담당 | 하는 일 |
| --- | --- | --- |
| 코디네이터 | Claude Opus 5.5 | 검색, 라이브러리 문서 확인, 작업 명세 작성, 스크린샷 확인, 배포, 이 글 초안 |
| 구현 | Codex 워커 | 장면과 조작 구현, Playwright로 브라우저 검증과 스크린샷 |

코디네이터는 워커의 완료 보고를 그대로 믿지 않고 스크린샷을 직접 열어 봤다. 반사 문제도 그렇게 찾았다. 이번에는 별도 모델의 코드 리뷰는 돌리지 않았다.

## 성능

워커가 Apple M4 Pro의 Chromium에서 1920×1080으로 측정한 값이다.

| 위치 | FPS |
| --- | ---: |
| 게이트 앞 | 60 |
| 거리 중간 | 53.1~55.4 |

라이브러리의 적응형 화질 조절이 켜져 있어서, 프레임을 지키려고 내부 해상도를 낮춘다. 측정 때 실제 그리기 해상도는 게이트 앞 1240×697, 거리 중간 942×530이었고 조명은 그 20% 해상도로 계산했다. 그래서 화면이 전체적으로 약간 부드럽게 보인다.

## 배포

정적 파일뿐이라 fly.io에 nginx 컨테이너 하나로 올렸다. 도쿄 리전, shared-cpu-1x 256MB 머신 1대이고 접속이 없으면 멈춘다. 라이브러리와 three.js는 jsDelivr에서 버전을 고정해 불러온다. 첫 배포에서 IP 자동 할당이 실패해서 IPv4와 IPv6를 따로 붙였다. 배포 뒤에 브라우저로 열어 콘솔 오류 0건, 52fps로 그려지는 것을 확인했다.

## 남은 것

1. 실제 휴대폰에서는 성능을 재지 않았다. 모바일은 M4 Pro에서 터치를 흉내 내서 확인한 것뿐이다.
2. Safari와 Firefox에서는 확인하지 않았다.
3. 별도 코드 리뷰를 받지 않았다.
4. WebGL2가 없는 환경에서는 레이트레이싱 없이 일반 렌더링으로 바뀐다.
