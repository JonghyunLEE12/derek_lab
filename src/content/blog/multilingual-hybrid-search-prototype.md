회사 서비스의 검색 개선 설계를 맡으면서 한 가지 원칙을 정했다. **운영 코드에 넣기 전에, 설계가 문서 위에서만 그럴듯한 게 아니라 실제로 돌아가는지 로컬에서 끝까지 확인한다.** 그래서 운영 저장소와 완전히 분리된 독립 검증 서버를 만들었다. 이 글은 그 프로토타입의 설계 결정과, 돌려 보고 나서야 알게 된 것들의 기록이다.

문제 상황은 이렇다. 서비스는 14개 locale(ko, en, zh-CN, zh-TW, zh-HK, ja, vi, th, id, ru, ar, ms, mn, fil)의 사용자를 받고, 시술·병원·숙소·매장·지도 장소라는 성격이 다른 다섯 도메인을 한 검색창에서 다룬다. 키워드 검색(BM25)은 이름을 아는 사용자에게는 잘 동작하지만, "통증 적고 오래 유지되는 시술"이나 "한옥 감성에서 전통문화를 체험하는 숙소" 같은 자연어 질의에는 0건을 돌려준다. 여기에 임베딩 기반 의미 검색을 더하되, 임베딩 인프라가 장애여도 기존 검색이 멀쩡해야 한다는 게 요구사항이었다.

## 구성

전부 로컬에서 재현 가능한 스택으로 맞췄다.

| 구성 요소 | 선택 | 역할 |
| --- | --- | --- |
| API/워커 | NestJS 11, Node 24 | API 1개 + 색인 워커 2개 |
| 원본·원장 | PostgreSQL 17 + pgvector | 원본 테이블, 검색 원장(벡터 보관), outbox |
| 검색 | OpenSearch 3.4 | BM25 + k-NN(HNSW, cosine, 1024차원), RRF |
| 캐시·신호 | Redis 7 | 질의 벡터 캐시, 사전 pub/sub, 워커 깨우기 |
| 임베딩 | 호스트 Ollama `bge-m3` (1024차원) | 색인·질의 임베딩, Metal GPU |
| 재순위 | `BAAI/bge-reranker-v2-m3` (CPU) | 외국어 의미 질의의 최종 관문 |

Ollama를 쓴 이유는 단순하다. API 키 없이, 외부 전송 없이, 노트북에서 다국어 임베딩 모델을 돌릴 수 있어서다. bge-m3는 14개 locale을 전부 커버하는 몇 안 되는 선택지였다. OpenSearch 3.4를 고른 건 k-NN, neural-search, ml-commons가 기본 배포에 포함되고 native RRF(score-ranker-processor)를 쓸 수 있어서인데, 이건 실제로 `_cat/plugins`를 찍어 보고서야 확정했다.

## 색인 파이프라인: outbox가 전부다

가장 공들인 부분은 검색 품질이 아니라 **원본과 색인의 정합성**이다. 원본 DB와 검색 인덱스는 서로 다른 저장소라 반드시 어긋나는 순간이 온다. 그래서 색인 요청을 별도 메시지 큐가 아니라 원본과 **같은 PostgreSQL 트랜잭션**에 넣었다.

```text
어드민 저장
  원본 변경 + revision 증가 + outbox UPSERT  ← 전부 한 트랜잭션
  커밋 후 pg_notify + Redis로 워커 깨우기 (1.5초 폴링은 안전망)
워커 2개
  SKIP LOCKED로 클레임 → 임베딩 해시 비교 → 바뀐 것만 재임베딩
  → 현재 상태 재조회 → 전체 문서 교체
```

여기서 배운 세부 사항들:

- **lease 기반 소유권.** 워커가 죽어도 작업이 유실되지 않도록 클레임에 60초 lease를 걸고 15초마다 갱신한다. 만료된 PROCESSING은 다른 워커가 재클레임하고, 반복 만료는 횟수를 세어 FAILED로 보낸다. claim token으로 소유권을 확인하므로 좀비 워커가 늦게 써도 무시된다.
- **이벤트가 아니라 상태로 판정한다.** "수정됨", "삭제됨" 같은 이벤트 종류로 색인을 결정하면 순서가 꼬였을 때 틀린다. 워커는 항상 DB의 현재 노출 상태를 다시 읽어서 색인할지 지울지 정한다. 원본이 없으면 삭제, 비노출이면 문서만 삭제하고 원장(벡터)은 유지한다. 재노출 때 본문이 같으면 재임베딩이 없다.
- **단조 증가 revision으로 늦은 쓰기를 막는다.** 원장 upsert는 `source_updated_at` 비교, OpenSearch는 `external_gte` 버전으로 오래된 문서의 재삽입을 거절한다. 실제로 하드 삭제 후 오래된 버전을 다시 밀어 넣는 실험을 했고 409로 거절되는 걸 확인했다.
- **인덱스는 버전 + alias로 운영한다.** 새 매핑은 새 인덱스(v2, v3)를 만들어 백필하고, 문서 수가 같고 outbox가 비었을 때만 alias를 전환한다. 롤백 검증 기간에는 이전 버전 쓰기를 유지한다.

## 장애 격리: 임베딩이 죽어도 검색은 산다

임베딩 provider는 가장 자주 죽는 의존성이라고 가정했다. 그래서 세 겹으로 쌌다.

1. **Circuit breaker** - 연속 3회 실패하면 30초간 열리고, 열림 상태는 Redis로 모든 워커가 공유한다. 중요한 건 circuit이 열려도 **클레임·삭제·lexical 색인은 계속한다**는 것. 임베딩 호출만 건너뛴다.
2. **격벽(bulkhead)과 예산** - 질의 경로와 색인 경로의 동시 호출 한도를 분리(8/2)해서 색인 폭주가 검색 지연으로 번지지 않게 했다. 시간당 호출·토큰 예산은 Redis Lua로 원자적으로 제한한다.
3. **lexical 먼저, 벡터는 나중에** - 임베딩이 실패하면 기존 벡터를 보존한 문서를 먼저 색인해서 이름·키워드 검색은 즉시 최신화하고, 벡터 재시도만 61초 → 2분 → 10분 → 30분 백오프로 미룬다.

이걸 말로만 두지 않고 독립 API에 임베딩 연결 실패를 주입해서, lexical 결과가 유지되는 것과 3회 실패 후 circuit이 열리는 것, provider가 돌아오면 연기된 행들이 자동으로 당겨지는 것까지 직접 관찰했다.

## 검색 경로: BM25 + k-NN + RRF, 그리고 거절 게이트

검색은 locale 정규화(`ru-KZ → ru`, `tl → fil` 같은 규칙) → 정확 일치 사전 → 동의어·지역 확장 → BM25와 k-NN 병렬 실행 → RRF 융합 순서다. 질의 벡터는 프로세스 LRU 500개 + Redis TTL 7일로 캐시하고 same-key 동시 요청은 single-flight로 합친다.

생각보다 어려웠던 건 융합이 아니라 **거절**이었다. k-NN은 무슨 질의를 넣어도 "가장 가까운" 문서를 돌려준다. "자동차 정비소"를 검색한 사용자에게 코사인 유사도 0.71짜리 시술을 보여주면 안 된다. 그래서 엄격 BM25가 0건인 의미 질의에는 벡터 최소 점수 게이트를 뒀다. 로컬 표본에서 무관 질의의 최고점(약 0.707~0.728)과 정답 질의의 최저점 사이인 **0.735**로 한국어 기준을 정했는데, 이 값은 표본에 전적으로 의존하는 임시값이다. 영어로 같은 측정을 반복하니 무관 질의 하나가 0.7377로 한국어 기준을 넘어 버려서 en 전용 기준을 분리해야 했다.

오타 교정도 이 단계에 있다. 한글은 자모 분해 필드에 fuzzy match(자모 길이에 따라 거리 0/1/2)를 걸고, 엄격 매칭이 0건일 때만 교정 결과로 대체한다. 라틴·키릴 문자는 별도 fuzzy 단계(최소 5자, 질의 토큰 전부가 이름·별칭에 편집 거리 내 매칭)를 따른다. 정상 결과 1건을 오타 교정이 덮어쓰지 않는 게 원칙이다.

## 재순위: 벡터 점수만으로는 안 되는 언어가 있다

다국어 검증에서 제일 재미있는 문제가 나왔다. 의미 질의와 무관 질의의 벡터 점수 분포를 locale별로 재 보니, 영어·중국어·일본어·러시아어는 기준값 하나로 정답과 무관을 분리할 수 있는데 **베트남어와 태국어는 두 분포가 겹쳐서 어떤 기준값으로도 분리가 안 됐다**(여유가 음수). bge-m3 임베딩 공간에서 언어별 밀도가 다르기 때문으로 보인다.

해결은 cross-encoder 재순위였다. 외국어 엄격 0건 질의에 한해 벡터 상위 후보 4개를 `bge-reranker-v2-m3`로 채점하는데, 해당 언어 설명과 영어 설명을 **분리 채점한 뒤 문서별 최대 점수**를 쓰는 방식이 모든 locale에서 dev 표본을 분리했다. 모델과 tokenizer는 revision을 고정하고 offline 모드로 로드하며, CPU 추론은 슬롯 4개·대기 한도·20초 타임아웃으로 묶었다. 재순위 서비스가 죽으면 locale별 벡터 게이트로 폴백하는데, 이 폴백이 재순위와 같은 회수율을 보장하지 않는다는 것도 명시적으로 기록했다 - vi/th는 보수적 기준 때문에 의미 회수율이 떨어진다.

기준값 보정 절차는 ML 평가의 기본기를 따랐다. dev 표본으로 기준을 정해 해시·동결 시각과 함께 기록한 뒤에 holdout을 실행하고, holdout으로는 기준을 조절하지 않는다. 그래도 locale당 표본이 작아서 이 기준들은 실험값이고, 운영에서는 라벨 50건 이상을 모아 재보정해야 한다고 결론에 적었다.

## 결과: lexical 28/35 vs hybrid 35/35

운영 형태의 CSV 복사본(5개 도메인 45건, 저장소에는 포함하지 않음)으로 질의 35개를 돌렸다. 이름 검색, 다국어 이름 검색, 자연어 의미 질의, 무관 질의(0건이 정답), 오타 질의를 섞었다.

- 전체: lexical **28/35**, hybrid **35/35**
- 자연어 의미 질의만: lexical **1/7**, hybrid **7/7**
- 무관 질의 4개: 두 모드 모두 0건 (게이트가 k-NN 꼬리 후보를 잘라냄)
- 오타 9개: 전부 정답 1위 + 교정어 반환

의미 질의 확장판(6개 외국어 × 의미/무관 × dev/holdout, 총 149개)에서는 hybrid 144/149였다. fixture 골든셋의 nDCG@10은 lexical 0.8257 대 hybrid 0.9746. 다만 이 수치들은 작은 표본의 배선 확인이지 품질 증명이 아니라서, 숫자 자체보다 "lexical이 구조적으로 못 잡는 질의 유형을 hybrid가 회수한다"는 패턴 확인에 의미를 뒀다.

실패 사례도 그대로 남겼다. "바닷물 수영장에서 놀 수 있는 숙소" 질의는 여전히 일반 해변 숙소를 정답보다 앞세운다. 시설 보유 여부 같은 사실 관계는 임베딩 유사도가 아니라 구조화 필드로 풀어야 한다는 숙제다.

## 배운 것들

1. **정합성 설계가 검색 품질보다 먼저다.** RRF 튜닝은 반나절이면 되지만, outbox·lease·버전 가드 없이는 "검색 결과가 원본과 다른데요"라는 문의가 끝없이 나온다. 늦은 쓰기 거절(409)을 실험으로 확인했을 때가 이 프로젝트에서 가장 안심된 순간이었다.
2. **의미 검색의 절반은 거절이다.** 무관 질의에 그럴듯한 결과를 보여주는 순간 신뢰가 깨진다. 그리고 그 거절 기준은 언어마다 다르고, 표본에 민감하고, 어떤 언어에서는 단일 기준으로 아예 불가능하다.
3. **폴백 경로의 품질 차이를 문서화해야 한다.** "재순위가 죽으면 벡터 게이트로 폴백한다"고만 쓰면 운영자는 같은 품질이라고 가정한다. vi/th 폴백은 회수율이 떨어진다고 명시한 게, 나중에 모니터링 지표를 나눠 보는 근거가 됐다.
4. **로컬 전 구간 재현의 가치.** 임베딩 장애 주입, lease 만료 주입, 오래된 문서 재삽입, circuit 공유까지 전부 노트북에서 실험했다. 운영 환경에서는 엄두가 안 날 실험들이 로컬 독립 서버에서는 몇 분짜리 작업이다.

다음 단계는 운영 평가셋으로 거절 기준을 재보정하는 것과, 시설·날짜 같은 사실 조건의 구조화 필터, 그리고 다국어 설명이 비어 있는 문서들의 데이터 보강이다. 결국 검색 품질의 마지막 병목은 모델이 아니라 데이터였다.
